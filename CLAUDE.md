## Tech stack

- Backend: Node.js + Express 5, TypeScript (strict)
- Database: PostgreSQL via Neon (serverless) + Prisma ORM 7, connected through `@prisma/adapter-neon` (Prisma 7 requires a driver adapter — plain connection strings in `schema.prisma` no longer work; the URL lives in `prisma.config.ts` for CLI/migrate use, and the adapter is passed directly to the `PrismaClient` constructor at runtime)
- Auth: JWT access tokens (Bearer header) + httpOnly-cookie refresh tokens with rotation, Google OAuth (`google-auth-library`), bcryptjs for password hashing, `cookie-parser` for reading the refresh/CSRF cookies
- Country/currency/timezone reference data: `world-countries` (currency, calling code) + `countries-and-timezones` (IANA timezone) + `currency-codes` (ISO 4217 decimal precision, added 2026-07-22) — real npm packages, not hand-authored; see "Global Reference Data" below for the full audit
- Validation: Zod (env validation belongs in `src/lib/config.ts`)
- Security middleware: Helmet, `cors` (env-driven allowlist via `CORS_ORIGINS`, `credentials: true` now that cookie-based auth exists — do not reintroduce an `origin: true` fallback outside dev, that combination is a real hole with credentialed cookies), `express-rate-limit`
- Scheduling/date math: `node-cron` (in-process hourly scheduler, `src/lib/reminderScheduler.ts`, added 2026-07-26 — first real scheduler in this repo) + `date-fns` (calendar-aware period arithmetic for interest calculation, `src/lib/interestEngine.ts`, same session) — both real npm packages, latest at the time
- Email: `resend` (official Node.js SDK, added 2026-08-06, Module 33 Session 4A) — real transactional email sending, behind a dedicated `EmailProvider` interface (`src/notifications/`), never imported outside `ResendEmailProvider.ts`; see "Real Email Sending — Module 33 Session 4A" below. `RESEND_API_KEY`/`RESEND_FROM_EMAIL` env vars, both optional/fail-soft. `svix` (added 2026-08-09, Module 33 Session 4B) — real webhook-signature verification for Resend's inbound email webhook; a genuinely separate, unbranded library (not the Resend SDK, does not touch the Architecture Lock). `RESEND_WEBHOOK_SECRET`/`RESEND_INBOUND_DOMAIN` env vars, both optional/fail-soft; see "Email Conversation Sync — Module 33 Session 4B" below.
- Testing: Jest + ts-jest + Supertest, run against the live Neon DB (no separate test DB exists — known risk; any test that creates data must clean up after itself, e.g. via a `cleanupTestBusiness` helper)

**Foundation:** `Business` (plan/tier/country-derived currency & timezone, no Somalia hardcoding, `settings` JSONB catch-all; gained `businessDayStartTime`/`businessDayEndTime` `@db.Time` columns 2026-07-22, defaults `00:00:00`/`23:59:59` — the single source of truth for Void/Refund day-boundary eligibility, see "Sales" below), `User` (email is the primary login identifier, not phone; `passwordHash` nullable for Google accounts; `failedLoginAttempts` incremented atomically), `Branch`, `Warehouse` (exactly one per business, enforced via `@unique` on `businessId`).

## Auth architecture (locked)

- **Signup + Login (built, 2026-07-20 — `src/{services,controllers,routes}/auth.*`, `src/lib/{session,otp,googleAuth,countryReference,businessSettings}.ts`):**
  - `POST /auth/signup` — one endpoint, both paths (`provider: "email" | "google"` discriminated union). Collects Business Name, Owner Name, Business Email (email path) or Google `idToken` (google path — the account's own verified email is used, never a client-supplied email, so a signup can't claim an email it doesn't control), WhatsApp Phone, Password (email path only), Country. Country auto-fills currency/timezone/phone-prefix via the `world-countries` + `countries-and-timezones` npm packages (real reference data, not hand-authored — neither package alone covers all three fields) — all three remain client-overridable per the locked spec. `Business.tier`/`plan` are hardcoded (see Known schema gaps). Terms/Privacy acceptance required (`termsAccepted`/`privacyAccepted: true`, literal booleans). Signup **auto-issues a session** (access token + refresh/CSRF cookies) — the owner is logged in immediately, doesn't need a separate login step after signing up.
  - WhatsApp phone-verification OTP is sent at signup (`OtpPurpose.signup`) but is **non-blocking** — nothing in the locked spec says phone verification gates account usability, unlike email. Verified separately via `POST /auth/signup/verify-phone-otp` (this endpoint wasn't explicitly pre-approved in the implementation plan; added because a send-only OTP with no way to complete it would be a dead end — flagging here rather than silently expanding scope).
  - Email verification (email path only — Google's own `email_verified` claim satisfies it immediately on the google path, same "presenting the token is the proof" logic Staff Invitation already uses): a token is emailed at signup, verified via `GET /auth/verify-email/:token`. Single-use by construction — the token is cleared on success, so a replayed link fails the lookup rather than needing a separate "already verified" check (a real, since-fixed bug: that separate check was originally unreachable dead code once the token-clearing behavior is in place).
  - `POST /auth/login` (email+password) and `POST /auth/google/login` — separate endpoints, matching the doc's naming (`login` vs `google/login`). `POST /auth/google/identify` — not spec'd behaviorally anywhere except the name; implemented as a pre-check the frontend calls after obtaining a Google ID token, before deciding whether to render a login or signup flow: verifies the token, returns `{exists, hasPasswordAccount, email, name}`. **This is an interpretation, not a certainty** — confirm if a real frontend ends up wanting something different.
  - **Google account-linking:** a Google login matching an existing *password-only* account (no `oauth_provider` set) is a hard `409`, never a silent auto-link. Confirmed decision, not a default — verified no code path can create a second user row or touch the existing one's `password_hash` for this case.
  - **Password policy:** min 8 chars, 1 upper, 1 lower, 1 number, 1 special char (`passwordSchema` in `src/lib/password.ts`, reused everywhere a password is set). Last 3 passwords blocked from reuse (`password_history`, populated on every account-creating/password-setting path).
  - **Lockout:** 5 failed attempts → `locked_until = now + 15min` (`FAILED_LOGIN_LOCK_THRESHOLD`/`FAILED_LOGIN_LOCK_MINUTES` in `auth.service.ts`, not env vars — deliberate, promote to config if that ever needs to be tunable). The lock check runs *before* password verification, so a correct password during an active lock still gets `423`, not a bypass. Counter resets to 0 on any successful login.
  - **Email verification gates:** `emailVerifiedAt` is real now, but nothing currently reads it as a gate — Password Reset (the thing it's documented to gate) is out of scope this pass. Security-alert emails and staff-invite acceptance's own verification are unaffected (staff-invite has its own, separate verification-by-token-possession logic, unrelated to this field).
- **Staff Invitation (built, 2026-07-20 — `src/{services,controllers,routes}/staffInvite.*`):**
  1. Owner enters Full Name, Email, Phone, Role (`POST /staff/invite`, owner-only, `manager` deliberately excluded — confirm if that's wrong).
  2. System emails an Accept Invitation link: `${APP_BASE_URL}/invite/<token>`.
  3. Invitee clicks → `GET /staff/invite/:token` shows business name + role → sets a password + checks a Terms/Privacy consent box → `POST /staff/invite/:token/accept`.
  4. Account activates immediately, `email_verified_at` set at that moment (presenting the mailed token *is* the verification). **No OTP anywhere in this flow.**
  5. Same login rule applies afterward: email + password only — now real, via `POST /auth/login`.
  - Invitable roles exclude `owner`/`super_admin` (enforced server-side via the Zod enum, not just UI). Invite token is 256-bit random, stored in `staff_invites.token` as plaintext (not hashed) — a deliberate choice matching the schema's own naming (contrast `sessions.refresh_token_hash`, which is hashed); revisit if that stops feeling right.
  - No resend/list/revoke-invite endpoints exist yet — a duplicate pending invite for the same business+email is a hard 409, not a resend.
  - QA caught and this fixed a real race: accepting the same invite token twice concurrently used to be able to 500 instead of cleanly 409 (the invite-claim wasn't atomic). Fixed by claiming the invite via `updateMany({ where: { id, accepted_at: null } })` and checking the row count *before* creating the user, inside the same transaction — not relying on an incidental `users.email` unique-constraint collision as the safety net. Regression test: `tests/staffInvite.accept.test.ts` ("only lets one of two concurrent accepts win").
  - Known minor gap, not fixed: `passwordSchema` (`src/lib/password.ts`) has no max length. Low risk (100kb body limit already bounds it), but worth a cap if this becomes a concern later.
- **New Device / High-Risk Login:** optional per-business toggle in `Business.settings` (`security.requireOtpForNewDevices` JSON key, default OFF — read via `src/lib/businessSettings.ts`). ON: a device is "known" only while it has an **active** session (`revoked_at: null`, `expires_at > now`) for that exact `(user_id, device_id)` pair — logging out (or a session expiring) resets that device's trust, it does not stay recognized forever. OFF (default): no OTP ever, on any device. QA caught and this fixed a real gap: the original check only tested whether a session had *ever* existed for that device, so a logged-out or revoked device stayed permanently trusted even with the toggle ON, silently defeating the feature. Regression tests: `tests/auth.login.newDeviceOtp.test.ts` ("re-challenges a device once its only session has been revoked/expired"). The OTP itself (`OtpPurpose.new_device_login`) goes via WhatsApp under the `SECURITY` category — a deliberate carve-out from the general Notification Routing rule below (SECURITY is normally email-first); the challenge has to reach the device being verified, so WhatsApp isn't optional here the way it is for other SECURITY alerts. No session/tokens are issued while `requiresOtp: true` is pending — verified no `Set-Cookie` header on that response. `otp_challenges.max_attempts` (5) locks the challenge after repeated wrong codes.
- **Refresh tokens:** httpOnly cookie (`refresh_token`, path `/auth`, never in the JSON body) + a readable double-submit `csrf_token` cookie, both reissued on every login/refresh. `requireCsrf` middleware (`src/middleware/csrf.ts`, timing-safe compare) gates only `POST /auth/refresh` and `POST /auth/logout` — the two endpoints that act purely on the ambient cookie; signup/login/google endpoints establish a *new* session rather than acting on one, so they're deliberately not CSRF-gated. In production the cookies are `SameSite=None; Secure` (the frontend is a separate origin per this doc's own "still separate HTML/React prototypes" note), which means the double-submit cookie is the *primary* CSRF defense here, not decorative — cross-origin `SameSite=None` cookies bypass the browser's own same-site protection. **Remember-me mechanics:** every refresh updates the *same* session row — new `refresh_token_hash` (rotation; the old raw token stops matching anything and further use of it is rejected), `expires_at` reset to `now + 7d` **unconditionally** regardless of `remember_me`, while the reissued cookie's own `Max-Age` (30d / 12h) is computed fresh from `remember_me` every time, not just at login. This reconciles "`expiresAt` is always 7 days" (true at every point it's written) with remember-me actually working across repeated use — a remembered session's 7-day DB window keeps sliding forward as long as the up-to-30-day cookie prompts activity; a non-remembered session's 12h cookie vanishes client-side long before the 7-day server cap would matter. **Accepted gap:** rotation updates in place rather than chaining session rows, so replayed-old-refresh-token *reuse detection* isn't built (the schema has no `previous_hash`/`replaced_by` column) — a stolen-then-rotated-away token simply fails on reuse (safe), but there's no alerting/family-revocation on that event.
- QA caught and this fixed a second real race, same TOCTOU class as staff-invite's: two concurrent signups with the same email could have the loser hit an uncaught Prisma `P2002` → generic `500` instead of a clean `409` (the pre-transaction existence check is a courtesy, not a guard — the unique constraint is the real one). Fixed by catching `P2002` on the `tx.users.create()` call inside the transaction and re-throwing as `conflict()`. Regression test: `tests/auth.signup.test.ts` ("only lets one of two concurrent same-email signups win").
- **RBAC:** `requireRole(...roles)` middleware. `super_admin` bypasses every check. `custom` role is fail-closed (403) until a permissions-evaluation engine exists — `User.permissions` JSON is present but unused, don't wire partial support for it. `req.auth` (set by `authenticate.ts`) carries `{userId, businessId, role, name}` — `name` was added 2026-07-21 (pulled from the JWT payload, which already had it) specifically so every business-module service can audit-log without an extra DB round trip to look up the actor's name; `staffInvite.service.ts` predates this and still does its own lookup, which is fine, just don't copy that older pattern in new code.
- **Void vs Refund (Sales) — built 2026-07-22, Session 3B:** Void = same business day only, by the cashier who created it (owner/super_admin also pass; manager does **not** bypass — enforced via `requireRole` excluding manager entirely from the route, plus a service-level `sale.cashier_id === actor.userId` check for the cashier case specifically), restores inventory using the sale's original item quantities inside the same transaction. Refund = after day-close only, owner/manager only, financial-only — no inventory restore (that stays with the not-yet-built Returns module); creates a separate reversal `Sale` row (`refundOfSaleId`, every money figure negated) rather than modifying the original's financial fields. **Day-close is now schema-backed, not hardcoded**: `Business.businessDayStartTime`/`businessDayEndTime` (defaults `00:00:00`/`23:59:59`, reproducing the prior "same calendar day in `Business.timezone`" rule exactly) via `src/lib/businessTime.ts`'s `getBusinessDay`/`isSameBusinessDay`. Both a sale already voided and a sale already refunded are blocked from the other transition (and from repeating the same one) by one atomic guarded `status` update (`WHERE status = "completed"`) — see "Sales" below for the full reasoning on why that's read as compliant with "never modify the original Sale financially."

## Global Reference Data — Country / Currency / Timezone / Phone (audited + closed 2026-07-22)

Pre-Session-4 audit, done before Debts got built on top of this foundation (due dates, business-day math, future reports/localization all depend on it being right). Verified the schema, all migrations, the Auth implementation, and the registration flow directly before writing anything — full findings below, not just the fixes.

- **No database table has ever mirrored this data, and none should.** `businesses.country`/`phone_prefix`/`timezone`/`currency` are plain resolved scalar columns, not FKs into a lookup table — confirmed via full-text search of `schema.prisma` and every migration. This is intentional: a hand-copied `countries`/`currencies`/`timezones` table would need manual upkeep every time ISO/IANA data changes, exactly what "never hand-maintain global datasets" rules out. **Locked decision: keep it this way** — module-level in-memory computation from maintained npm packages stays the single source of truth, no DB-backed cache, confirmed after review, don't second-guess this in a later session.
- `world-countries@5.1.0` (250 entries incl. territories) + `countries-and-timezones@3.9.0` (IANA zones, UTC/DST offsets, alias resolution) — both confirmed to be the latest published versions, nothing to upgrade. New `currency-codes@2.2.0` added this session (ISO 4217 decimal-precision/`digits` data neither of the other two packages has).
- **`src/lib/countryReference.ts`** — `getCountryDefaults` (existing, used by signup) plus new `getAllCountries`/`findCountry`/`getCountryTimezones`/`isValidTimezoneForCountry`/`getPhonePrefix`/`getValidPhonePrefixes`/`isValidPhonePrefixForCountry`. **`src/lib/currencyReference.ts`** (new) composes `currency-codes`' code/name/digits with `world-countries`' per-country currency symbols into one `{code, name, symbol, digits}` record per currency — symbol is `null`, never fabricated, for the ~50 ISO codes with no single-country association (XAU, XDR, etc.).
- **A real, pre-existing bug found and fixed**: `idd.root + idd.suffixes[0]` (the original phone-prefix formula, used by real signups) is correct for the overwhelming majority of countries, but wrong for exactly two well-documented real-world telephony exceptions where multiple sovereign ISO territories share one *identical, complete* ITU country calling code with no country-level digit beyond the root: **NANP** (`+1` — US, Canada, Jamaica, Bahamas, Puerto Rico, ~25 total) and **Russia/Kazakhstan** (`+7`, a USSR-era holdover). For these, `idd.suffixes` is a *local area/trunk code*, not a country-code continuation — the old formula produced `+1201` for the United States instead of the correct `+1`. QA independently caught that my first pass only special-cased NANP, missing `+7` — verified this can't be derived generically from the dataset's root/suffix shape alone (some *other* shared roots, e.g. Réunion/Mayotte both genuinely being `+262`, are correctly handled by the plain formula and must NOT be collapsed to root-alone) — so `getPhonePrefix`'s `ROOT_ALONE_IS_COMPLETE_CODE` is an explicit, small, real-world-verified set (`"+1"`, `"+7"`), not a generic heuristic. Both `getCountryDefaults` and the new reference API's country-summary builder call this one shared helper — no duplicated logic to drift out of sync again. Regression tests: `tests/countryReference.unit.test.ts`, `tests/auth.signup.test.ts` ("resolves the plain +1 phone prefix for a NANP country").
- **New, unauthenticated `GET /reference/countries?search=`, `GET /reference/countries/:countryCode/timezones`, `GET /reference/currencies?search=`** (`src/{services/referenceLookup,controllers/reference,routes/reference}.*`) — deliberately public, same reasoning as `/auth/signup` itself (needed *before* an account exists). Bidirectional search over name/official-name/cca2/cca3/phone-prefix. Response envelope is `{data: [...]}` with **no pagination** — an intentional, documented exception to the usual `{data, pagination}` rule, since these are small, bounded (≤250 items), non-business-data lookups, not paginated resource lists. **`Cache-Control: public, max-age=604800` (7 days)** on all three routes (`reference.routes.ts`'s own local `cacheControl` middleware — not a repo-wide pattern, scoped to this module since it's the only one where a week-old cached response is still correct) alongside Express's untouched default weak `ETag`. 7 days because this data only changes on a deliberate `world-countries`/`countries-and-timezones`/`currency-codes` version bump + redeploy (see above) — there's no legitimate reason for a client to refetch sooner. The two headers are complementary: `max-age` lets a client skip the network entirely for a week; `ETag` is what makes the *next* request past that window cheap (a conditional GET gets a `304` instead of the full payload) and is also what protects a client that ignores/clears `max-age` early — it always reflects current content, never stale.
- **Timezone "city" labels are a display convenience only** (`"America/New_York"` → `"New York"`, mechanically derived from the IANA identifier's last path segment) — explicitly **not** a "major city" dataset (no population/lat-long/official-designation data backs it) and must never be treated as one. Locked decision from review.
- **Server-side country/timezone/currency/phone-prefix consistency validation, added to `resolveCountryFields` (`auth.service.ts`)**: a signup's explicit `timezone`/`currency`/`phonePrefix` override is now validated as actually belonging to the selected `country` before being accepted — previously any non-empty string was trusted blindly. **QA caught and this fixed a real gap**: my first pass only validated `timezone`/`currency`, leaving `phonePrefix` completely unchecked (an attacker could submit any string). Now all three are validated the same way, via `isValidPhonePrefixForCountry`/`isValidTimezoneForCountry`/direct currency-key membership. This is the sole call site for `getCountryDefaults` — both the `email` and `google` signup branches go through it, so there's no second unvalidated path. Regression tests: `tests/auth.signup.test.ts` (mismatch → `400` for all three fields; a legitimate-but-deprecated timezone alias like `Africa/Mogadishu` for Somalia is still correctly *accepted*, not just the canonical `Africa/Nairobi`).
- **Locked decisions from review, no code impact, documented so a later session doesn't redo this work**: UI languages (English/Arabic/French/Spanish/Somali, expandable later) are a small, separate, application-level concept from `world-countries`' per-country *spoken* languages — not a world-language database, nothing built this session. Scope stays locked to what Session 4 actually needs — number formatting, currency symbol position, measurement systems, tax regions, fiscal calendars, and full localization (date format / time format / week-start-day columns on `Business`) are explicitly deferred, not forgotten; this reference layer is designed as a clean extension point for Customers/Reports/Analytics/Business Settings/multi-country expansion when those sessions actually happen, not built preemptively now.

No rate limiter attached (rate limiting only exists on `/auth`/`/staff` routes so far — consistent with hardening roadmap Session 9 "distributed rate limiting" being not-yet-started, not a regression).

**Products** (`src/{validation,services,controllers,routes}/product.*`) — `POST /products`, `GET /products` (paginated), `GET /products/:id`, `PATCH /products/:id`, `DELETE /products/:id` (archive), `POST /products/:id/restore`, `POST /products/:id/stock-adjustment`.

- **RBAC (a deliberate design split, not from explicit doc spec):** create/update/archive/restore = owner+manager only. List/get = owner+manager+accountant+storekeeper (accountant needs cost visibility for reporting; storekeeper needs to know what they're stocking). Stock-adjustment = owner+manager+storekeeper (storekeeper is the role that actually does physical stock counts). Cashier is excluded from every Products endpoint — POS-only, product lookups for checkout belong to the not-yet-built Sales module, not general product management. Shareholder and `custom` get no access anywhere, per the general rule.
- **Optimistic locking, for real this time:** every mutating endpoint (update/archive/restore) requires the client to send the `version` it last read; the write is `updateMany({where: {id, version: expectedVersion}, data: {..., version: {increment: 1}}})`, checking the returned count — a stale version is a clean `409`, not a silent overwrite. Same pattern for stock-adjustment against `branch_inventory.version`.
- **Categories:** `categoryId` is validated for same-business ownership via `getOwned` if supplied, but **there is no Category CRUD module in this repo** — categories can currently only be created via direct DB access. Not an oversight; Categories was never asked for as its own module. Don't build features that assume category management exists through the API.
- `images` is deliberately not exposed anywhere in the API — dormant field (no upload feature exists), stays at its DB default.
- **Cost-price-change → PriceHistory:** `PATCH /products/:id` requires a `reason` **only** when `costPrice` is actually changing (compared via `Prisma.Decimal.equals()`, so string/number formatting differences like `"10.00"` vs `10` correctly don't count as a change) — not when other fields change, not when `costPrice` is sent but numerically unchanged. When it does change, writes a `price_history` row inside the same transaction as the product update. `sellingPrice` changes are **not** tracked in PriceHistory — only `costPrice`, matching what was actually asked.
- **Stock-adjustment direction is client-supplied, not inferred from `adjustmentType`** — confirmed decision. `correction`/`opening_balance`/`transfer` don't have an unambiguous inherent direction the way `increase`/`decrease`/`damage`/`loss`/`found` do, so the request body carries both `adjustmentType` (why, for audit/reporting) and `direction: "increase"|"decrease"` (which way stock actually moves) as separate fields. If no `branch_inventory` row exists yet for `(branch, product, size)`, an `increase` creates one (covers `opening_balance`); a `decrease` against nothing is a clean `409`. The lookup accounts for the documented `size IS NULL` dedup limitation (picks one row deterministically, doesn't corrupt data if duplicates exist — QA-verified, see below).
- **Money/quantity precision:** `costPrice`/`sellingPrice`/`minStockLevel`/stock-adjustment `quantity` all reject input with more than 2 decimal places at the Zod layer (`decimalField()` in `product.schema.ts`) — added after QA found that sub-cent input (e.g. `10.001`) used to slip through, get treated as "changed" by the pre-rounding `Decimal.equals()` compare, and either write a phantom PriceHistory row (`old_price === new_price` after DB rounding) or trip a DB `CHECK` constraint mid-transaction and surface as an unhandled `500`. Now rejected cleanly at `400` before reaching the service.

**QA caught and this fixed a genuinely critical bug**, found outside the specifically-requested scrutiny areas: `updateProductSchema` originally reused `sizes`/`unitType`/`packagingHierarchy` field definitions that carried `.default(...)` (meant for create). Zod's `.default()` substitutes whenever the resolved value would be `undefined` — including "key omitted from the request" — **regardless of `.partial()`** being applied on top. Every `PATCH /products/:id` that didn't explicitly resend all three fields was silently wiping them back to `[]`/`"each"`/`{}`, overwriting real data on any ordinary partial update (e.g. changing just the `sku`). Fixed by giving `updateProductSchema` its own non-defaulted definitions for those three fields instead of reusing the create-only versions. Regression test: `tests/product.qa.additional.test.ts` ("a PATCH that only changes sku must NOT reset sizes/unitType/packagingHierarchy"). This is exactly the kind of bug `.partial()` + `.default()` combinations should be assumed to have until proven otherwise — watch for the same pattern in Sales/Debts/Expenses' update schemas.

## Sales — Session 3A (Sale Creation), built 2026-07-22

`src/{validation,services,controllers,routes}/sale.*` — `POST /sales`, `GET /sales` (paginated, filters: `status`/`branchId`/`dateFrom`/`dateTo`), `GET /sales/:id`. Void/Refund (`POST /sales/:id/void`, `POST /sales/:id/refund`) were deliberately isolated from this session per the user's own framing — see "Sales — Session 3B" immediately below for those.

- **`sales.items` is a JSON column, not a relational table.** The live schema already locked this shape before this session started — Requirement "each line permanently stores its price snapshot" is satisfied by what `createSale` writes into that JSON array (`productId`/`productName`/`size`/`quantity`/`sellingPriceAtSale`/`costPriceAtSale`/`lineSubtotal`/`discount`/`tax`/`profit`), never a separate `SaleItem` table.
- **Architecture decision — Inventory Ledger:** extended the existing `inventory_adjustments` table (new `AdjustmentType` enum values `sale`/`void`) rather than building a parallel movements table. One row per line item, `reason: "Sale ${sale.id}"` for traceability. Confirmed with the user before implementation. (Originally shipped without a `sale_id` FK column, reasoning "nothing programmatic needs that join yet" — the user flagged this before 3B started, and it was right: `inventory_adjustments.saleId` was added in 3B, see below, and `createSale`'s own inserts were retrofitted to populate it too.)
- **Architecture decision — Sale Number vs Receipt Number:** `sales.id` (already a `generateId()` UUID) *is* the immutable, never-reused Sale Number — no schema change needed for it. Receipt Number is new: `receipt_id` now gets populated with `INV-<business-local-year>-<6-digit-sequence>`, sequential per business per year, backed by a new `receipt_counters` table (`business_id`+`year` unique, `last_number`) and a single atomic `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING` statement (`src/lib/receiptNumber.ts`) run inside the sale's own transaction — never `SELECT MAX+1`. Year is computed from `Business.timezone` via a new `src/lib/businessTime.ts` (`getBusinessLocalYear`), written as a general utility (not receipt-number-specific) so Session 3B's Void/Refund day-close check reuses it instead of re-deriving timezone math.
- **Idempotency-Key, built for real for the first time** (`idempotency_keys` table already existed but nothing read/wrote it before this session): `src/middleware/idempotencyKey.ts` (`requireIdempotencyKey` — 400 if the header is missing, thin/validation-only like `csrf.ts`) + `src/lib/idempotency.ts` (`getReplayedResponse`/`claimIdempotencyKey`/`completeIdempotencyKey`). Two-phase: claim happens as the *first* write inside `createSale`'s own `$transaction` (relies on the table's `@@unique([business_id, key, endpoint])` constraint — a collision throws `conflict()`, rolling back the whole attempt and leaving the key free if the earlier attempt genuinely failed); complete happens as the *last* write in the same transaction, storing the exact JSON-normalized response body so a replay is byte-identical to the original. QA-verified this closes the true-concurrent-brand-new-key race (two simultaneous requests sharing a never-before-seen key — exactly one 201, the other a clean conflict, never a second sale). Designed for reuse as-is by Debts' payment endpoint (and 3B's Void/Refund) per the original session-breakdown plan — no new lib code expected there.
- **Stock decrement is atomic-conditional, not read-then-write** — worth being explicit about given the existing documented `branch_inventory` NULL-size dedup gap (a plain btree unique index doesn't dedupe `size IS NULL`, so more than one qualifying row can theoretically exist). Per line: a `findFirst` (deterministic `orderBy: id asc`) picks **which row** to target — unavoidable given that gap — but the accept/reject decision itself is made by the DB, atomically, in the same `updateMany` statement that writes (`WHERE id = row.id AND quantity >= requestedQty`), re-verified against live state at write time, not from the earlier read. For the common case (non-null `size`) the unique index guarantees `findFirst` can only ever match one row anyway.
- **Money math is entirely `Prisma.Decimal`, never `number`/`float`.** Client sends one optional sale-level `discount` (`fixed`|`percentage`) and one optional `taxRate` (percentage); server prorates both down to each line by that line's share of subtotal, remainder assigned to the last line, so per-line amounts always sum exactly to the sale-level totals. **QA caught and this fixed a real Decimal-rounding bug**, found outside the specifically-requested scrutiny areas: each line's raw subtotal (`sellingPrice × quantity`) was originally summed *unrounded* for the sale-level `subtotal`, while each line's own stored snapshot was rounded to 2dp independently — two lines each with a raw subtotal of exactly `0.005` each round *up* to `0.01` individually (stored sum `0.02`), while the true unrounded total (`0.01`) rounds to `0.01` once. Fixed by rounding each line's subtotal to 2dp at the single point it's first computed and using that same rounded value everywhere downstream (sale-level sum, discount/tax proration base, and the stored snapshot) — sale-level `subtotal` is now the sum of the lines by construction, not by coincidence. Regression test: `tests/sale.test.ts` ("keeps item-level lineSubtotal snapshots summing to the exact sale-level subtotal").
- No price-override field this session — the spec only named it in the audit-events list ("if applicable"), nothing in the schema marks a line as overridden, and nothing else asked for it by name. `sellingPriceAtSale` is always the product's current `selling_price` at sale time. Flag if a real price-override capability is actually wanted — cheap now, more disruptive once 3B builds on this shape.
- No packaging-level conversion on sale lines (unlike Products' stock-adjustment endpoint) — a line's `quantity` is in the same base ("each") unit `branch_inventory.quantity` already tracks. `inventory_adjustments` rows written by a sale record `packaging_level: "each"`.
- **RBAC (inferred, not a copy of the actual 8-role recovery-doc matrix — that document isn't a file in this repo):** create = owner/manager/cashier (cashier explicitly doc-confirmed; storekeeper explicitly has zero sales access, also doc-confirmed). List/get add accountant (reporting/reconciliation visibility, same reasoning as Products' accountant read-access). Shareholder/custom: no access anywhere, matching every other module. Flag if the real matrix says otherwise.
- **`decimalField()`** (the 2dp-precision Zod guard) moved from `product.schema.ts` into `src/validation/common.schema.ts` and is now exported/shared — `product.schema.ts` imports it instead of keeping its own copy. Behavior-identical; existing Products tests are the regression check (still passing).
- **Extension points verified, none built this session** (per explicit user instruction — see the Session 3A plan for the full table): CRM/Customer Purchase History (`customer_phone` already the natural join key), Accounting (figures already server-computed/immutable), Debt Module (`debts.sale_id` already exists, nullable — zero Sale-side change needed), Reports/Analytics (every needed field already exists, read-only), Notification Events (`SaleCreated` — no event bus existed yet at the time, real gap; built for real in 3B, see below), Branch-level Inventory isolation (already true from Session 2's schema, this session inherits it directly), Business Timezone/Daily Session Close (`getBusinessLocalYear` deliberately general-purpose — 3B added `getBusinessDay` alongside it in the same file).
- No per-sale notification is sent (no `SaleCreated` → WhatsApp/Email spam) — matches the explicit "notification restraint" requirement; sale creation only saves data and writes the audit trail. (`SaleCreated` *is* published as a domain event as of 3B — that's not the same thing as a notification; see below.)

## Sales — Session 3B (Void, Refund), built 2026-07-22

`src/services/sale.service.ts` gained `voidSale`/`refundSale`; `src/{controllers,routes}/sale.*` gained `POST /sales/:id/void` and `POST /sales/:id/refund`. Builds directly on 3A's ledger and receipt-numbering shape — the Architecture Lock rule for this session was "extend, don't rebuild," and nothing in 3A's shape needed to change to accommodate this.

- **Final State Protection** (a sale reaches exactly one terminal state — `Completed→Voided` and `Completed→Refunded` allowed, all four other transitions/repeats forbidden) is enforced by **one atomic guarded status update** on both paths: `tx.sales.updateMany({ where: { id, business_id, version, status: "completed" }, data: { status: newStatus, ... } })`, checking `result.count`. A `count === 0` covers "already voided," "already refunded," and "modified concurrently by another request" all at once, symmetrically, with no separate existence-check query needed.
- **"Refunds must never modify the original Sale" is read as the financial record specifically, not lifecycle status** — a deliberate interpretation, stated up front for review rather than assumed silently. Refund transitions the original's `status` (`completed`→`refunded`, same atomic guard as Void) but never touches `subtotal`/`discount`/`tax_amount`/`total`/`profit`/`items` — those stay exactly as `createSale` wrote them, permanently. Taken completely literally (zero field writes including `status`), Final State Protection becomes unenforceable atomically without a second existence-query, which is what this reading avoids.
- **Refund reversal** = a brand-new `sales` row (`refund_of_sale_id = original.id`, a column that already existed in the live schema before this session — the DB was designed for exactly this shape). Every money figure negated 1:1 from the original (`subtotal`/`discount`/`tax_amount`/`total`/`profit` all ×`-1`) so `total = subtotal − discount + tax` still holds for the reversal row too. `items` copied verbatim (informational — refund is financial-only, no inventory write at all). Gets its own new receipt number from the same per-business-per-year sequence (a refund is its own customer-facing financial event, not free). `chk_sales_total_nonneg: CHECK (total >= 0 OR refund_of_sale_id IS NOT NULL)` — confirmed by reading the live constraint before writing this code, not assumed — already permitted a negative total specifically for this case; zero migration needed for it.
- **No `refund_reason` column** — `sales.void_reason` already existed for Void and is populated directly; there's no analogous refund field, and reusing `void_reason` for refunds would be actively misleading. The refund reason is required at the Zod layer and stored in the `AuditLog` entry (`sale.refunded`), this repo's existing canonical "why" record.
- **Exact inventory restoration on Void** — reads the sale's own immutable `items` snapshot (3A's price-locked JSON, never recomputed from current stock) and atomically increments `branch_inventory` by those exact quantities, one `inventory_adjustments` row per line (`adjustment_type: "void"`, `sale_id` set). `adjustment_amount` is stored positive (`quantityAfter − quantityBefore`) — the mirror of how a sale's own decrement stores `quantityBefore − quantityAfter` — required by the live `chk_inventory_adj_amount_positive` constraint.
- **Business Day is now schema-backed** (`Business.businessDayStartTime`/`businessDayEndTime`, `src/lib/businessTime.ts`'s `getBusinessDay`/`isSameBusinessDay`) rather than hardcoded same-calendar-day math — see the schema section above and the Auth Architecture's Void-vs-Refund entry. `businessDayEndTime` is stored but **not yet read** by Void/Refund eligibility (a rolling 24h window from `start` alone is sufficient and unambiguous for that purpose) — it becomes load-bearing whenever Daily Reports/Cash Closing/Shift Closing get built. Unit-tested directly in `tests/businessTime.unit.test.ts` (non-default start times, the boundary instant itself, month/year/leap-year rollover, a non-whole-hour-offset timezone) — added during this session's QA pass specifically because the integration tests only ever exercised the *default* start time.
- **Domain events are real now, not just documented extension points**: new `src/lib/events.ts`, a typed `EventEmitter`-backed `domainEvents.publish(name, payload)` singleton for `SaleCreated`/`SaleVoided`/`RefundCreated`. Published strictly **after** each operation's transaction commits, never from inside it. `createSale` (3A) was retrofitted to publish `SaleCreated` too, for consistency. No subscriber exists yet anywhere in this repo (Notification/Analytics/CRM/Accounting are all still unbuilt) — this is the publish side of the loose-coupling rule ("Sales must never call those modules directly"), proven by tests attaching a temporary listener, not by an actual subscriber.
- **RBAC**: Void = owner/cashier only (`requireRole("owner", "cashier")` — **manager is deliberately excluded from the route entirely**, unlike everywhere else in this module where manager has broad access; `super_admin` still bypasses via `requireRole` itself). A cashier may only void **their own** sale (`sale.cashier_id === actor.userId`, enforced in the service — role membership alone can't express per-resource ownership). Refund = owner/manager only, no cashier, no per-sale ownership restriction (any owner/manager can refund any sale in the business).
- **Idempotency-Key reused as-is** from 3A's `src/lib/idempotency.ts` (no new lib code, matching the original session-breakdown plan) — both new endpoints require the header and use the same claim-inside-transaction/complete-at-the-end two-phase pattern, scoped per-sale (`POST /sales/${id}/void` as the logical endpoint string, not a bare `"POST /sales/:id/void"`, so a reused key can never cross-contaminate a different sale's operation).
- **QA caught and this fixed two real bugs**, both outside the specifically-requested scrutiny areas:
  - `tests/helpers/cleanup.ts` nulled `sales.refund_of_sale_id` before bulk-deleting to break the self-referencing FK — but a refund reversal row's negative `total` is only permitted by `chk_sales_total_nonneg` *while* that FK is still set, so nulling it first violated the constraint the moment any test created a real refund. Fixed by deleting reversal rows (`refund_of_sale_id IS NOT NULL`) before the rows they reference, instead of nulling anything.
  - Under genuine 5-way concurrent sale creation, one request threw a Prisma `P2028` (interactive-transaction timeout, 5s default). Root cause: `getNextReceiptNumber`'s atomic per-`(business, year)` counter row is a deliberate serialization point — that's what atomic sequential numbering requires — and Neon's serverless HTTP driver adds real per-query latency, so a transaction queued behind several others waiting on that same row can legitimately exceed 5s under load with nothing actually deadlocked. Fixed by raising the transaction timeout to 15s (`SALE_TRANSACTION_OPTIONS` in `sale.service.ts`, applied to all three of `createSale`/`voidSale`/`refundSale`).

## Debts — Reminder Scheduler + Interest Engine, built 2026-07-26

Extends Session 4 Debts with two things: a real automated Reminder Scheduler, and a real Interest Engine (Session 4 only had interest *configuration* fields — nothing ever calculated or charged interest until now).

### Reminder Scheduler (`src/lib/reminderScheduler.ts`, new)

`node-cron`, ticking hourly. Each tick (`discoverAndSendReminders`) iterates every business, reads its `getDebtReminderSchedule` (unchanged from Session 4), and for each `open`/`partially_paid` debt calls the *exact same* `sendReminder` function the manual `POST /debts/:id/remind` endpoint already used — one true send path, never a second parallel delivery pathway, per the Session 4 locked decision. Scheduler-triggered sends use the business's own `owner_id` as the audit-log-FK-valid actor, `userName: "Reminder Scheduler"`, so the audit trail is honest about *who* triggered it without a schema change to `audit_logs`. Started on process boot in `src/index.ts`.

- **DB-level idempotency (not app-level locking) is the real guarantee.** `debt_reminders` gained `business_date` (`@db.Date`) + `@@unique([debt_id, reminder_type, business_date])`. `sendReminder` was restructured into a claim/complete two-phase pattern (`claimReminderSlot`, private helper in `debt.service.ts`) — mirroring the exact claim/complete shape this repo already uses for Idempotency-Key: claim via `create(..., status: "pending")`, a `P2002` on the unique constraint means another call (manual click, concurrent scheduler tick, a second server instance) already claimed this exact debt+type+business-day, so skip and return the existing row; only then does the actual WhatsApp send happen; complete updates that same row to `sent`/`failed`. `ReminderStatus` gained `pending` for the claimed-but-not-yet-sent state. Verified under genuine concurrency (`tests/reminderScheduler.test.ts`, two `discoverAndSendReminders()` ticks fired via `Promise.all` on the same debt) — exactly one `sent` row survives, never two WhatsApp sends.
- **`overdueDays` is a grace period, not "the instant it becomes overdue."** QA caught the scheduler's first pass ignoring `schedule.overdueDays` entirely — `isOverdue` alone triggered eligibility starting day 1 overdue regardless of what grace period a business configured. Fixed: eligible only once `daysPastDue >= schedule.overdueDays`, symmetric with how `beforeDueDays` already gates the "before due" side. Regression test: `tests/reminderScheduler.test.ts` ("does not send an overdue reminder before the configured overdueDays grace period has elapsed, but does once it has").
- **Accepted, narrow gap, not fixed**: the initial `pending` claim runs outside any transaction, before the WhatsApp send is attempted. If the process crashes (or a DB error occurs) in that narrow window before the completing transaction runs, that debt+type+business-day slot is stuck at `pending` for the rest of that calendar day with no reclaim path (only `failed` rows are reclaimable) — silently skipping one day's reminder, then self-healing the next business day. QA-flagged, narrow blast radius, deliberately left as a documented gap rather than rushed — same category as the refresh-token reuse-detection gap already accepted elsewhere in this doc.

### Interest Engine — 3-tier policy model

- **Tier 1 (system capabilities)**: `InterestType` (existing: `none`/`fixed`/`percentage`) + new `CalculationPolicy` (`one_time`/`daily`/`weekly`/`monthly`), `InterestFormula` (`simple`/`compound`), `PercentageBase` (`original_amount`/`remaining_balance`).
- **Tier 2 (defaults)**: `getDebtInterestPolicy` (new, `businessSettings.ts`, same defensive-read pattern as `getDebtReminderSchedule`) — `{enabled: false, type: "none", ...}` when a business hasn't configured anything. Interest is never silently on.
- **Tier 3 (per-business config)**: `Business.settings.debts.interestPolicy` — the only place real values live. No global default rate anywhere in code.
- **Policy snapshot on the debt, the fairness-critical part — real behavior change from Session 4.** `createDebtSchema` now **rejects** `interestEnabled`/`interestType`/`interestValue` as client input (silently stripped by Zod, not a validation error) — Business Settings is the sole source of truth for financial policy, so a client-suppliable override would defeat that. `createDebt` reads the business's *current* policy via `getDebtInterestPolicy` and snapshots all six fields (`interest_enabled`/`interest_type`/`interest_value`/`calculation_policy`/`formula`/`percentage_base`) onto the new debt at creation time — copied once, never a live lookup at calculation time. A later `Business.settings` edit only affects debts created *after* the edit; every existing debt keeps calculating under whatever was snapshotted when it was created. QA independently traced the call graph (`getDebtInterestPolicy` is called exactly once in the whole codebase, inside `createDebt`) and confirmed this holds. `debts` also gained `last_interest_applied_at` (`DateTime?`).
- **Calculation (`src/lib/interestEngine.ts`, new — pure functions, no DB access)**: `getPeriodsElapsed` — `one_time` fires exactly once ever (0 on every call after `last_interest_applied_at` is first set); `daily`/`weekly` are exact fixed-length periods (`date-fns` `differenceInCalendarDays`, floored `/7` for weekly — not `differenceInCalendarWeeks`, which counts calendar week-boundary crossings, a different semantic); `monthly` uses `differenceInCalendarMonths` for true calendar-month arithmetic (Jan 31→Feb 28 = 1 month, Mar 31→Apr 30 = 1 month), never a fixed 30-day approximation. `calculateInterest` — `fixed` = `rate × periods`; `percentage`/`simple` = `base × (rate/100) × periods`; `percentage`/`compound` = `base × ((1+rate/100)^periods − 1)`, where `base` is `principal` or `remainingBalance` per `percentageBase`.
- **QA caught and this fixed a real, live money-correctness bug**: `last_interest_applied_at` is a genuine wall-clock timestamp (unlike `date_taken`/`today`, which are already UTC-midnight-anchored calendar dates) — feeding it raw into `date-fns`' `differenceInCalendarDays`/`differenceInCalendarMonths` (which read **local** `Date` getters, not UTC and not `Business.timezone`) meant `periods_elapsed` silently depended on the *server process's own local timezone* from the second `apply-interest` call onward. QA reproduced this live (Node resolving to `America/Los_Angeles` in this sandbox, sweeping a fixed UTC calendar day hour-by-hour flipped the period count mid-day). Fixed by bucketing `last_interest_applied_at` through the business's own `getBusinessDay` before any calendar arithmetic, exactly like `today` already was (`applyInterest` in `debt.service.ts`). Regression test: `tests/debt.test.ts` ("computes daily periods_elapsed from the business's own calendar day, independent of last_interest_applied_at's stored wall-clock hour").
- **`POST /debts/:id/apply-interest`** (owner/manager only, mirrors Refund's elevated bar; Idempotency-Key required; optimistic-locked via `version`, same shape as every other debt mutation). Loads the debt's *own* snapshotted policy (never Business Settings), computes periods elapsed, calls the pure engine, and if the result is `> 0`: atomically updates `amount_remaining` + `last_interest_applied_at` + `version`, recomputes `status` (see below), writes an immutable `debt_transactions` row, audit-logs, publishes `InterestApplied`. If computed interest is `0` (e.g. `one_time` already applied, or not enough time elapsed), responds `200` with the unchanged debt and no new ledger row — not an error.
- **QA caught and this fixed a second real bug**: `applyInterest` updated `amount_remaining` without calling `recomputeStatus`, unlike every other balance-changing mutation (`recordPayment`/`reversePayment`). Interest only ever increases the balance, so a `partially_paid` debt whose accrued interest pushed `amount_remaining` back up to/above `amount_original` kept the stale `partially_paid` label instead of reverting to `open` per this module's own "status is purely derived from the amounts" rule. Fixed; regression test in `tests/debt.test.ts`.
- **New `debt_transactions` table** — immutable ledger, never updated or deleted (same rule as `audit_logs`). Built generically extensible (an 8-value `transaction_type` enum covering `interest_applied`/`interest_adjustment`/`payment`/`payment_reversal`/`discount`/`write_off`/`refund`/`debt_created`), but **only `interest_applied` is actually written this session** — `payment`/`refund`/etc. deliberately stay in their existing Session 4 tables (`debt_payments`, `audit_logs`), not migrated; that's a separate, riskier piece of work nobody asked for yet. Typed relational columns, not a JSON blob (`amount`, `balance_after`, `interest_type`/`interest_formula`/`percentage_base`/`calculation_policy`/`interest_rate_applied`/`periods_elapsed` all nullable — only populated on interest-related rows). **QA caught a real gap**: this table shipped without a CHECK constraint, unlike every other financial table in this repo. Fixed via migration `20260726144416_debt_transactions_check_constraints`: `chk_debt_transactions_amount_nonzero` (`amount != 0`, not `> 0` — `amount` is deliberately a signed column so a future `payment_reversal`-style row can still be negative, mirroring `debt_payments`' own reversal convention; `!= 0` only rules out a meaningless zero-amount row) and `chk_debt_transactions_balance_after_nonneg` (mirrors `debts.amount_remaining`'s own existing nonneg CHECK).
- **`tests/helpers/cleanup.ts`** gained a `debt_transactions.deleteMany` line — the new table FKs to `debts`; without deleting it first, cleanup fails with an FK violation (caught during this session's own verification, not by QA).
- **Automated interest accrual was explicitly not built this session** — `apply-interest` is a manual trigger, same shape Session 4 used for reminders before its own scheduler existed. Adding an automated accrual tick later is a small follow-up (reuse the reminder scheduler's discovery-loop shape), not a redesign, now that real scheduling infrastructure (`node-cron`) exists in this repo.

## Low Stock Alert (Module 02), built 2026-07-28

Closes the one remaining gap in Module 02 (Inventory Management) — `products.min_stock_level` has existed since Session 2 but nothing ever read it. Real triggers on both places `branch_inventory.quantity` actually decreases (Sale line-item decrement, stock-adjustment `decrease`), a persisted per-row debounce so WhatsApp fires exactly once per low-stock episode, a `StockLow`/`StockRecovered` domain-event pair, and a genuinely reusable message-template registry. - **Debounce is a persisted state pair directly on `branch_inventory`, not a query against event/audit history**: `low_stock_alert_active` (Boolean) + `low_stock_alerted_at` (DateTime?), migration `20260728071214_low_stock_alert_debounce`. Both fields are written **atomically inside the same transaction** as the quantity change that crosses the threshold — the debounce state itself can never be wrong or duplicated, only the notification *delivery* is best-effort (see the accepted tradeoff below). No new Prisma enum for severity — it's never persisted, only computed on the fly for the event payload/message, so `StockSeverity` is a plain TS union in `src/lib/stockAlerts.ts`, matching how `NotificationCategory`/`NotificationChannel` are already plain TS unions rather than DB enums.

The one place this doesn't need the gate is a **brand-new opening-balance row** (stock-adjustment's `!existing` branch in `product.service.ts`) — a fresh row starting below threshold has no real prior debounce state at all, so that one call site still just skips the check entirely rather than calling through with `direction: "increase"`.

Code-level registry (functions/objects), not an admin-editable CMS. Registers `low_stock_alert` and `stock_recovered` (the latter registered for completeness even though nothing sends it yet — recovery is event+audit only, see below). **Translation confidence note, carried forward from the templates' own code comments**: English/French/Spanish/Arabic are high-confidence; Somali is a functional first pass, not verified by a native speaker — needs a real review before being trusted for production business communication.

- **Hook-in points**: `sale.service.ts`'s `createSale` (per line-item decrement) and `voidSale` (inventory restoration — confirmed as a recovery trigger point, not just stock-adjustment's increase direction, since a voided sale that restores stock above threshold must be able to clear an active alert on that row); `product.service.ts`'s `adjustProductStock` (both directions, on the `existing`-row branch only — see above). `adjustProductStock`'s pre-existing ownership-check fetch (`getOwned(prisma.products.findUnique(...))`) previously discarded its return value — now captured as `const product = ...` to get `min_stock_level` in scope at zero extra query cost. `adjustProductStock`'s transaction now does one extra read (and, on a transition, one extra write) versus before this session — given Neon's serverless HTTP driver latency and the exact same `P2028` interactive-transaction-timeout class already documented under Sales, its transaction timeout was raised to 15s (`STOCK_ADJUSTMENT_TRANSACTION_OPTIONS`, same fix, same reasoning as `SALE_TRANSACTION_OPTIONS`). `createSale`'s decrement loop and `voidSale`'s restore loop each re-read `branch_inventory` via a fresh `findUniqueOrThrow` **immediately after** their own guarded write succeeds, inside the same transaction, and use *that* committed row (never the pre-write `findFirst` snapshot) to compute `quantityAfter`/`wasActive` and the `inventory_adjustments` ledger's `quantity_before` — see the QA-caught bugs below for why the original pre-write-snapshot approach was wrong.
- **Accepted tradeoff, documented not hardened this session (confirmed explicitly, not silently decided)**: the debounce *state* is fully transactional as described above — never duplicated or lost. Only the *notification delivery* (the subscriber's async work, running after commit via `EventEmitter`, which does not await async listeners) is best-effort. If the process crashes between commit and the subscriber finishing, the row is correctly left `active`, but because the debounce is now active, no later crossing re-fires a notification until that episode recovers and drops again — so a crash-lost alert can stay silently missed for the rest of that entire episode, not just one instant. This is accepted as reasonable for a best-effort notification (nothing financial is at risk; the underlying stock state itself is always correct) — **not** something to harden reflexively; whoever builds the next production subscriber on `domainEvents` should know this is the existing, chosen bar, not an oversight.
- **Explicitly out of scope this session, per your instruction**: Notification Escalation (severity-based recipient expansion to Purchasing/Procurement) and an in-app Notification Center (persistent dashboard, read/delete state, mobile push, badge counts) — the `StockLow`/`StockRecovered` payload shape was deliberately kept rich enough that a future Notification Center subscriber could build per-user records from it directly, without a redesign.
- **RBAC**: no new endpoints or roles — this session only adds a background event subscriber and hooks into three existing, already-RBAC-gated write paths (Sale creation/void, stock-adjustment).
- **QA caught and this fixed two real bugs, both found by real execution (a `Promise.all` concurrency script and a sequential HTTP repro against the live dev DB), not by static review** — an initial QA pass on this feature was blocked by an environment issue (a stale plan-mode flag falsely restricting the subagent to read-only tools); a second, genuinely fresh QA pass got real command access and found both of these:
  - **Concurrent sales/voids on the same `branch_inventory` row could double-fire `StockLow` and corrupt the `inventory_adjustments` ledger.** `createSale`'s decrement loop and `voidSale`'s restore loop originally computed `quantityAfter`/`wasActive` from the `findFirst` row read *before* their own guarded write, not from the row's true state after it. Postgres still serializes the actual `quantity` column correctly via row-locking (the DB-side number was always right), but the JS-side snapshot goes stale the instant a concurrent transaction's write commits in between — QA reproduced this live: two truly-concurrent sales each decrementing 3 from a `quantity=100`/`minStockLevel=97` row both independently read `wasActive=false` and both published `StockLow` (should be exactly one), and both wrote an identical, wrong `quantity_before=100/quantity_after=97` pair into `inventory_adjustments` (the second sale's row should have read `97→94`). Regression test: `tests/stockAlert.test.ts` ("concurrent sales on the same branch_inventory row never double-fire StockLow, and the ledger stays consistent").

Regression test: `tests/stockAlert.test.ts` ("raising min_stock_level via PATCH mid-episode does not cause a later increase to illegally fire StockLow").

## Customer Records — Module 05, built 2026-07-29

Formalizes a `customers` table and a find-or-create-by-phone pattern that already existed, built ad-hoc inside Debt's `createDebt` (Session 4) — this session extracts that into a real, shared module both Debts and Sales use, and closes two real gaps research found before writing any code: `sales` had never linked to `customers` at all (only a free-text `customer_phone`), and phone identity was a raw, un-normalized string with zero dedupe protection across formatting variants. Deliberately thin, per the locked spec — a sales-history tracker, not a full CRM.

**Research findings, confirmed by reading the live schema/code and a direct row-count check against the live dev DB before writing anything** (not assumed): `customers` had `id/business_id/phone/name?/email?/total_spent(unused anywhere)/debt_balance(actively maintained)/status/created_at`, no `version`, no indexes beyond `@@unique([business_id, phone])`, **0 live rows** (so the reshape below needed no backfill). ### Decision (Requirement #21 — customer auto-creation on Sale): wire Sales' existing `customerPhone` into the shared find-or-create

**Chosen: add the link, don't defer to Module 06 (Receipts).** `customerPhone` already existed in the schema/validation — the added work was small (one nullable `sales.customer_id` column, one call into the shared helper, cache updates in the same transaction) and fully backward-compatible (a sale with no `customerPhone` behaves byte-identical to before). Deferring would have left "Total Amount Spent" and the Sales portion of the Activity Timeline empty for most customers, since Sales — not Debts — is presumably the dominant transaction type; that's actively misleading on a profile page, not just incomplete. `createSaleSchema` also gained an optional `customerName` (mirroring Debt's shape) — without it, every Sales-provisioned customer would be permanently stuck with a null name.

### Schema

`customers` reshaped wholesale (0 live rows, confirmed, no backfill): `phone` → `phone_original` (raw, display-only) + new `phone_normalized` (E.164 via `libphonenumber-js`, a new dependency — the only field uniqueness/search/find-or-create ever key off); new `customer_number` (immutable, `CUS-000001`, `@@unique([business_id, customer_number])` — getting the per-business composite unique right from day one, unlike `expense_number`'s original global-unique bug that had to be fixed later); new derived caches `total_spent`/`purchase_count`/`total_debts`/`total_payments`/`last_purchase_at`/`last_debt_at`/`last_payment_at`/`last_activity_at` (same trust model as `debt_balance` — never authoritative, recalculable from source tables); new `archived_reason` (inferred addition, matching the Expenses/Sales precedent of a stored reason column, not just audit-log-only like Branches/PaymentMethods); new `version`/`updated_at`. Indexes: `@@index([business_id, phone_normalized])` (plain, non-partial — backs search across both active+archived rows, since archived customers stay fully searchable), `@@index([business_id, name])`, `@@index([business_id, last_activity_at])`, `@@index([business_id, debt_balance])`.

**Uniqueness among ACTIVE customers only, not a plain `@@unique`**: Prisma's schema DSL has no partial/filtered unique index syntax (same class of gap already documented for this schema's hand-added CHECK constraints). A plain `@@unique([business_id, phone_normalized])` would be wrong — it would block reusing a phone that only an *archived* customer holds, which is explicitly allowed. Enforced instead via a raw-SQL partial unique index, hand-added to the generated migration file: `CREATE UNIQUE INDEX ... ON customers (business_id, phone_normalized) WHERE status = 'active'`. This is the real guard against a concurrent duplicate-active-phone race (create or restore); app-layer pre-checks exist for a clean error message, not as the actual guard.

New `customer_counters` (mirrors `expense_counters` exactly, no year dimension). `sales` gained one nullable `customer_id` + relation + index — additive, a sale with no `customerPhone` gets `customer_id: null`, byte-identical to before this session. No changes to `debts` — its own `customer_id` FK already existed and was already correct.

### Shared `findOrCreateCustomer` — this repo's first cross-service import

New `src/services/customer.service.ts` exports `findOrCreateCustomer(tx, {businessId, phoneRaw, name, defaultCountry})`, imported by both `debt.service.ts` and `sale.service.ts` (kept strictly one-directional — `customer.service.ts` never imports either back). ### Two real concurrency bugs found by the implementer's own test (before QA even started) and fixed

- **Transaction-poisoning in `findOrCreateCustomer`.** The first version used the same `try { tx.customers.create(...) } catch (P2002) { return tx.customers.findFirstOrThrow(...) }` shape the *original* Session-4 `debt.service.ts` local function had used — a genuinely pre-existing latent bug, not something this session introduced, just never exercised by a real concurrency test until now. Under real concurrency (two requests racing to find-or-create the same brand-new phone), this produced a real 500: Postgres poisons an *entire* transaction after any failed statement (`current transaction is aborted, commands ignored until end of transaction block`, error 25P02) until an explicit ROLLBACK — Prisma's JS `try/catch` doesn't issue a SAVEPOINT around the failing statement, so the recovery `findFirstOrThrow`, still inside the same poisoned transaction, failed too. Fixed by replacing the whole pattern with one atomic `INSERT ... ON CONFLICT (business_id, phone_normalized) WHERE status = 'active' DO NOTHING RETURNING id` — this never throws on a lost race in the first place, so there's nothing to recover from mid-transaction. Regression test: `tests/customer.test.ts` ("no duplicate customer creation under concurrent requests").
- **The fix above's raw INSERT initially omitted `updated_at`** (caught immediately after fixing the first bug, by the same test) — `customers.updated_at` is a `@updatedAt` field with no database-level default; Prisma's generated `create()`/`update()` populate it at the application layer, which raw SQL bypasses entirely, so the INSERT hit `null value in column "updated_at" violates not-null constraint`. Fixed by setting `created_at = now(), updated_at = now()` explicitly in the INSERT.
- **A third gap, found via manual live-server stress testing beyond either test suite** (an 18-way, then 30-way, real concurrent `POST /customers` burst — well past the 8-way the committed test exercises): `P2028: Unable to start a transaction in the given time` — a *different* Prisma error class than the `timeout`-during-transaction P2028 this repo already has a documented fix for (Sales' `SALE_TRANSACTION_OPTIONS`). This one is `maxWait` (the time allowed to even *begin* a transaction, Prisma's default 2000ms) being exceeded while other transactions ahead of it serialize on the same `customer_counters` row — `CUSTOMER_TRANSACTION_OPTIONS` only extended `timeout`, not `maxWait`. Fixed by setting both (`{ timeout: 15000, maxWait: 10000 }`). Verified clean up to 18 real concurrent creates (matching the locked test requirement) with zero failures and 18 distinct sequential numbers; at 30-way, a handful of requests still legitimately time out, but the underlying guarantee never breaks — zero duplicate numbers were ever produced even then (confirmed live: `26 of 26` unique across a 30-way burst with 4 clean timeouts). **This is logged as an accepted capacity boundary, not a bug to chase further** — 30 staff simultaneously hand-adding brand-new customers on one business within the same instant is far beyond realistic usage, and the same unaddressed `maxWait` gap likely exists in Sales/Debts/Product's own transactions too (none of them set it either) — flagged here as a named follow-up for whoever next needs to stress-test one of those past its own already-documented 5-way precedent, not fixed preemptively in this session.

### Numbering, status-transition shape — reuses established patterns exactly

`src/lib/purchaseOrderNumber.ts`/`getNextPurchaseOrderNumber` + new `po_counters` table are a deliberate near-duplicate of `customerNumber.ts`/`expenseNumber.ts` (table identifiers aren't parameterizable via `Prisma.sql` bind params, so this repo never generalizes these into one shared helper) — same atomic `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING`, format `PO-000001`.

**Status transitions (send/confirm/cancel) use Sale's `voidSale` shape, not Debt's `transitionDebtStatus` shape** — the required source status is baked directly into the `updateMany`'s own `WHERE` clause (`{id, business_id, version, status: "draft"}` etc.), one atomic statement, `count === 0` throws a single `conflict()` covering both "wrong source status" and "concurrent race" uniformly. Debt's `transitionDebtStatus` does a separate JS pre-check before a version-only-guarded update — a real TOCTOU gap between the two steps. **This is logged here as a known, pre-existing architectural difference in already-shipped, fully-tested Debt code — not a bug, not in scope to fix this session**, per the plan's own confirmed framing: a future Debt-hardening candidate, nothing more.

**`updatePurchaseOrder` (PATCH) is a deliberate exception with a JS pre-check *in addition to* the atomic guard** — `if (po.status !== "draft") throw badRequest(...)` runs before the transaction starts, purely as a fail-fast optimization (nicer error, no wasted transaction for the common non-concurrent case), but the atomic `updateMany` still independently includes `status: "draft"` in its own `WHERE`. This does **not** reopen Debt's TOCTOU gap: unlike Debt's second step (version-only), PATCH's second step still carries the status condition, so a concurrent loser is correctly rejected either way — by the pre-check (400) or the atomic guard (409), whichever layer sees the stale state first. This is the exact same documented pattern Expenses' `approveExpense`/`markExpensePaid` already established ("both outcomes correctly reject the loser — only which layer catches it is timing-dependent"), reused here rather than reinvented. Regression test: `tests/purchaseOrder.test.ts` ("a concurrent PATCH racing a Send never lets both win").

### Somali-language clarifications, folded in as first-class locked requirements

- **PATCH is DRAFT-only in the fullest sense** — not just "status is locked," but line items, supplier, branch, currency, and every snapshot field may never be modified once a PO leaves DRAFT. Enforced by construction (see above), not by convention.
- **Explicit cross-business rejection, stated directly rather than left as an unstated `assertOwned` assumption**: supplier, every line item's product, and branch are all validated as belonging to the same business before a PO can reference them.
  - **Supplier and branch go through `getOwned` → a clean 404** (same-404-either-way, matching every other module).
  - **Products also go through `getOwned`'s `assertOwned` → a `404`** (fixed 2026-07-30, see below) — the batch-fetch (`WHERE id IN (...) AND business_id = ...`) is kept for the N+1-avoidance win, but each resolved row is now passed through `assertOwned(productMap.get(id), businessId, "Product")` instead of a bare `badRequest` on a map miss, so a missing-or-cross-business product is indistinguishable from a missing-or-cross-business supplier/branch by construction. **All four reference types this module ever validates (the PO itself, supplier, branch, product) now uniformly return 404 through the same `getOwned`/`assertOwned` helper — no mixed status codes remain anywhere in Purchase Orders' cross-business ownership checks**, re-verified by re-reading the whole service file end to end, not just the one call site being fixed. Archived-state checks (supplier/branch/product all-must-be-active) are a deliberately separate concern, uniformly `400` across all three — that's "belongs to you but isn't usable right now," not an ownership question, so it correctly stays a distinct status code from the 404 "doesn't belong to you" case.
- **2026-07-30 follow-up fix**: `createSale`'s own identical line-item-batch-validation shape still returns `400` for a missing/cross-business product — this asymmetry between Sales and Purchase Orders is now real and known, but **deliberately not touched this pass**, per explicit instruction: fixing Sales' own 400→404 behavior (and potentially building one shared generic ownership-check helper reused across every module's line-item-batch-validation path) is a legitimate future goal, scoped as its own dedicated session after Module 08, not bundled into Purchase Orders' own code or into Session B. `tests/sale.test.ts` was re-run in full (57/57 passing) to confirm zero impact from this Purchase-Orders-only change.

`purchase_order_items.unit_cost_snapshot` is **client-supplied** (the price negotiated with the supplier for this specific order) rather than auto-derived from `products.cost_price` — `productNameSnapshot`/`skuSnapshot` ARE auto-derived from the product's current values at creation time, matching `costPriceAtSale`'s exact auto-population behavior. ### Locked decisions (confirmed with the user before implementation, resumed from the interrupted prior session)

1. **GRN → PO status derivation**: `received` iff cumulative `quantity_received` (summed across every GRN received against a line) ≥ that line's `quantity_ordered`, for **every** line on the PO; `partially_received` otherwise. Over-delivery still counts as received — flagged via `variance_quantity`, never blocked. Implemented as a recomputation on every GRN creation (querying `goods_received_items.groupBy(["po_item_id"])` including the just-inserted rows), applied via a version-guarded `updateMany` — not a fixed-source-status FSM transition like send/confirm/cancel, since this is derived data, matching how Debt status is "purely derived from the amounts."
2. **3-way match tolerance — hardcoded, not a Business Settings field**: `tolerance = min(total_expected_value × 0.01, 10)` (1% or $10, whichever is smaller), compared against both `invoiceAmount` and the cumulative GRN-received value (`Σ quantity_received × unit_cost_actual` across every GRN for the PO), each vs. `total_expected_value`. The larger of the two variances is stored as `match_variance` and drives `match_status`; `match_failed` requires a `matchOverride.reason` or the request is rejected with `400` and the match details in `error.details` (`errors.ts`'s `badRequest(message, details)` already supported this, no change needed).
3. **Auto-created Expense category**: a 6th system category, **"Inventory Purchases"**, added to `expenseCategory.service.ts`'s `SYSTEM_CATEGORY_NAMES` — lazily seeded via the existing `ensureSystemCategoriesSeeded`, self-heals every business the same way the original 5 do. None of the original 5 (Rent/Electricity/Payroll/Transport/Misc) fit "money paid to a supplier for goods."
4. **Auto-created Expense workflow_status bypass**: created directly at `workflow_status: "paid"`, with `approved_by`/`approved_at`/`paid_by`/`paid_at` all stamped to the actor recording the payment — confirmed explicitly, not an oversight. ### QA-caught bugs (both found by the implementer's own testing before QA even started — a real, two-attempt fix history worth recording precisely)

- **`warehouse_stock`'s NULL-size dedup gap is not a rare edge case here — it's 100% of usage.** `branch_inventory` has the same long-documented limitation (a plain `@@unique([..., size])` doesn't dedupe rows where `size IS NULL`, since Postgres never matches `NULL = NULL`), but it's rare there because a real `size` value often narrows it. Every PO/GRN/manual-movement line item is size-less by construction, so `warehouse_stock` hits the NULL path on *every* write. A concurrency test (two simultaneous stock-ins of 3 each against a brand-new product) confirmed this live: both transactions read "no row exists yet" and both independently created their own row (two rows of 3, six total in the table) instead of one row correctly incremented to 6.
  - **First fix attempted**: a transaction-scoped `pg_advisory_xact_lock(hashtext(warehouseId), hashtext(productId))`, acquired before the read, released automatically on commit/rollback. This produced a genuine multi-hour hang in this environment during testing (root cause not fully confirmed — possibly the lock itself interacting with this stack's Prisma 7 + `@prisma/adapter-neon` serverless driver in some untested way, possibly unrelated; see the environment-issue note below, discovered investigating this same incident, for a separate, confirmed contributing factor). Abandoned rather than debug an unproven locking primitive against an unfamiliar serverless driver.
  - **Fix that shipped**: switched `warehouse_stock`'s "no size" sentinel from `NULL` to an **empty string** (`""`) — safe because this brand-new table has zero real size usage in this session and zero legacy rows. This makes the existing `@@unique([warehouse_id, product_id, size])` a *real* guard (Postgres treats two empty strings as equal), enabling a genuinely atomic single-statement `INSERT ... ON CONFLICT (warehouse_id, product_id, size) DO UPDATE ... RETURNING` for stock-in and a conditional `UPDATE ... WHERE quantity >= X RETURNING` for stock-out — the exact same atomic-counter pattern every numbering table in this repo (`po_counters`, `grn_counters`, `wsm_counters`, ...) already relies on and has been verified correct under real concurrency elsewhere. No advisory lock, no separate `findFirst`, no race window. Re-ran the concurrency test after the fix: correct (one row, quantity 6). Regression test: `tests/warehouseMovement.test.ts` ("never double-counts under concurrent stock-in on the same brand-new product").
- **`getOrCreateWarehouse` (`src/lib/warehouse.ts`) had the exact same transaction-poisoning bug Customer Records' `findOrCreateCustomer` already hit and fixed** — found by the implementer's own live concurrency stress test (a `Promise.all` burst of simultaneous first-ever stock-ins for one brand-new business, run directly against the dev DB via a throwaway script, beyond what the committed test suite exercises), not by the QA pass (which hit a real session-limit quota error mid-review this session — see the environment-issue note below). First version used `tx.warehouses.upsert(...)`: an 8-way burst showed only 1 of 8 succeeding, the other 7 throwing an unhandled P2002 (`Unique constraint failed on the fields: (business_id)`) surfaced as a `500` — `upsert`'s presumed atomicity didn't hold up under this stack's Prisma 7 + `@prisma/adapter-neon` interactive-transaction combination. Second attempt (find-then-`create()`-with-a-catch-P2002-fallback-SELECT) hit the *same* root cause Customer Records already documented: Postgres poisons the entire transaction after any failed statement (`current transaction is aborted, commands ignored until end of transaction block`, 25P02) until an explicit ROLLBACK, so the recovery SELECT — still inside that same poisoned transaction — failed too. **Fix that shipped**: the identical pattern already proven correct for `findOrCreateCustomer` — an atomic `INSERT ... ON CONFLICT (business_id) DO NOTHING RETURNING id`, which never throws on a lost race in the first place, so there's nothing to recover from mid-transaction; a lost race returns zero rows (not an error), and the follow-up `findUniqueOrThrow` runs in a still-healthy transaction. Re-verified live at 8-way and 15-way concurrency after the fix: 100% success both times, ledger `quantity_before`/`quantity_after` chain consistent, final quantity exactly matching `successCount × qty`.
- **`confirmPurchaseOrder`/`sendPurchaseOrder`'s own response bodies don't include `purchase_order_items`** (only `create`/`update`/`get` use `PO_ITEMS_INCLUDE`) — a pre-existing Session A shape, not a regression, but it broke naive test helpers that assumed a confirm response could be used directly to look up a line-item ID. Fixed at the test-helper level (`createConfirmedPo` in the new test files re-fetches via `GET /purchase-orders/:id` after confirming) — not a service-layer change, since the asymmetry itself is fine (list/get are the "full shape" endpoints by design, status-transition responses are deliberately lean).
- **`purchase_order_payments`/`goods_received_items` shipped without CHECK constraints** — the `///` schema-comment markers anticipating them were never backed by real SQL in the original draft. Same gap `debt_transactions` had before `20260726144416`; closed the same way, in the same session rather than waiting for a later QA pass to catch it: migration `20260802123336_grn_and_po_payment_check_constraints` adds `chk_goods_received_items_quantity_positive`/`_unit_cost_nonneg`, `chk_purchase_order_payments_amount_positive`/`_invoice_amount_nonneg`, `chk_purchase_orders_remaining_amount_nonneg`/`_paid_amount_nonneg`.
- **`expenseCategory.test.ts`'s "exactly 5 system categories" assertion** needed updating to 6 once "Inventory Purchases" was added — expected fallout from locked decision #3 above, not a bug; test updated in the same session.

### Known environment issue, discovered investigating the advisory-lock hang above: `TaskStop` does not reliably kill the underlying Windows process for a backgrounded Bash task

**Not a code bug in this repo — a second, distinct tooling/harness issue in the Claude Code environment (the first is documented above, "stale plan mode on freshly-spawned QA subagents").** While diagnosing what looked like a 90+ minute hang on a backgrounded `npx jest ... | tail -150` command, calling the harness's own `TaskStop` on that task ID returned a success message — but the actual underlying `node` process (and its `tail` pipe partner, and their parent `bash`) were still running and consuming resources **over two hours later**, confirmed via direct Windows process inspection (`ps`/`tasklist`/`Get-Process`) showing the exact original start timestamp. A second, unrelated background task later showed the same pattern from the other direction: its Jest run printed a final "Time: 133.881s" summary and a "Jest did not exit one second after the test run has completed... asynchronous operations that weren't stopped" warning, yet the harness continued reporting that task as `"running"` until the underlying process was force-killed directly (`Stop-Process -Force`), at which point the harness immediately surfaced a `"failed"` notification for it.

**Practical mitigation**: don't trust "stopped"/"still running" status alone for a backgrounded shell task when something looks stuck or a completed-looking task never notifies — cross-check directly against the OS (`ps aux` for MSYS PIDs plus the `WINPID` column, or `Get-Process`/`tasklist` for the authoritative Windows-level view) before concluding a process is genuinely hung, genuinely finished, or genuinely killed. A process actively consuming incremental CPU time across repeated checks is legitimately still working (this environment's real per-query Neon latency makes multi-minute jest runs normal, not evidence of a hang) — the concerning signal is zero CPU progress over a sustained interval, not merely "no notification yet" or "the file looks empty" (piping through `tail -N` also legitimately produces zero visible output until the piped process's input stream closes, which is a separate, non-alarming reason for an empty-looking output file). When a task truly needs killing, `Stop-Process -Force` (or `taskkill`) by the actual Windows PID is what has worked in this environment — the harness's own `TaskStop` alone has not been reliable for this.

The B2B negotiation layer on top of Module 11's already-`sent` Purchase Orders: a secure, token-authenticated supplier portal (no login — a supplier has no `users` row anywhere in this schema) for threaded messaging and versioned counter-offer negotiation, plus the matching owner-side authenticated API. Built from a very detailed user-supplied spec plus a 10-point "Architecture Enhancements (LOCKED)" addendum, treated as in-scope architecture for this session (not deferred backlog) specifically to avoid a future database redesign.

**Pre-code verification, per explicit instruction not to build on an assumed foundation**: Module 11 Sessions A and B were confirmed actually built by reading the live schema/services/tests directly (not assumed) — independently corroborated by the spec document itself, which already referenced this repo's own Session B work in past tense. - **`po_negotiation_agreement_snapshots`** (Enhancement #5) — one immutable row **per accepted proposal**, keyed by `negotiation_round` (not just "the latest one"), matching this repo's "keep every entry" ledger philosophy. `items_snapshot` JSON, `shipping_method`/`delivery_date`, `total_expected_value` — a permanent point-in-time record a later PO edit can never overwrite (nothing ever updates or deletes an existing snapshot row).

### Rejected alternatives (raised by a second review pass, declined with reasons per your explicit feedback — not silently omitted)

1. **Merging Internal Notes into messages via `sender_type: "internal"`** — rejected on security grounds: every future query against messages, especially any supplier-portal one, would need to remember to filter internal rows out; one forgotten `WHERE` clause away from leaking confidential notes to a supplier. ### Architecture — shared foundation

- **`NegotiationActor`** (`src/lib/negotiationActor.ts`) — a discriminated union (`{party:"owner",...}` / `{party:"supplier",...}`) shared between the owner-authenticated routes and the token-authenticated portal, so every negotiation service function (`createMessage`, `saveDraft`, `acceptProposal`, ...) is written exactly once regardless of which side calls it. **`resolveAuditActor(actor, po)`** solves a real constraint the spec didn't anticipate: `audit_logs.user_id` is a required real FK to `users`, and a supplier has no user account — reused the exact precedent the Debt Reminder Scheduler already established (a non-user trigger needing an FK-valid actor) by resolving supplier-originated audit rows to the PO's own `created_by`, with an honest `user_name` ("Supplier: Ahmed Hassan (+254712345678)") describing who actually acted, no schema change needed.
- **`secureLinkAuth`** (`src/middleware/secureLinkAuth.ts`) — the one unauthenticated (no JWT/session) route tree in this repo. Resolves `:token`, re-hashes via the existing `hashToken`, checks `status==="active" && expires_at>now`, attaches `req.secureLink`. Returns `404` for an unknown token, `410 Gone` for a found-but-inactive/expired one. Gated by a new `supplierPortalLimiter` (`src/middleware/rateLimit.ts`, 30 req/min/IP).

### Negotiation Status — derivation (`src/lib/negotiationStatus.ts`)

`computeNegotiationStatus(po, latestSubmittedProposal, secureLink, now)` — pure, JS-only, mirrors `decorateDebt`/`getDebt`'s shape (not `listDebts`' raw-SQL `CASE`, since this session has no list/filter endpoint needing to filter many POs by negotiation status at the DB layer, only a single-PO summary read). `cancelled`→`REJECTED`; anything past `sent` that isn't cancelled→`AGREED`; an expired deadline or an expired/revoked secure link→`EXPIRED`; a `pending` submitted proposal→`WAITING_SUPPLIER`/`WAITING_OWNER` depending on who submitted it; otherwise `OPEN`. ### Agreement — the accept transaction (`acceptProposal`, `src/services/poNegotiationProposal.service.ts`)

Owner-only in v1 (a locked default — supplier-side acceptance isn't exposed on the portal router at all this session). One atomic guarded `updateMany` (`WHERE id, status:"pending"`) claims the transition — `count===0` throws `409`, covering "already resolved" and "concurrent race" uniformly, same Final-State-Protection shape as Sale Void/Refund and PO Send/Confirm/Cancel. Every child `po_negotiation_proposal_changes` row is then applied via a structured `applyChange()` — never a raw PATCH — covering all 7 `field_changed` types (quantity/unit_price update the item + recompute `line_total`; `product_substitution` swaps `product_id`/snapshot fields after an active-status + no-duplicate-product check; `product_added` parses a `{productId,quantity,unitCost}` JSON payload and creates a new line; `product_removed` deletes one). `total_expected_value` is recomputed from the post-apply items (same derived-cache-recompute-at-the-one-write-point pattern PO's own PATCH-while-draft uses), `negotiation_round` increments, an Agreement Snapshot is written, audit-logged, `PurchaseOrderNegotiationAccepted` published post-commit.

**Interpretation flagged, not silently assumed**: `delivery_date`/`shipping_method` changes have **no corresponding live column on `purchase_orders` or `purchase_order_items`** — Module 11 Session A/B's own design never needed one. These two change types are captured only in the Agreement Snapshot's own `shipping_method`/`delivery_date` columns (what was agreed *this round*), not written to any mutable PO field. Chosen to avoid an unapproved schema expansion; flagging for confirmation before Session 2 (Shipments) potentially needs a real live field for either.

**Recording an advance payment never creates an Expense record.** `poAdvancePayment.service.ts`'s `recordAdvancePayment` never imports or calls `createExpenseInTransaction` — advance payments represent a Current Asset (prepayment for goods not yet received), not an operating expense; that's Session B's completely separate `purchase_order_payments` path. ### Proforma Invoice fallback source — interpretation flagged, not silently assumed

Blocking Proforma Invoice generation entirely for that common case would be a real product gap. **Resolved**: `issueProformaInvoice` reads the latest Agreement Snapshot when one exists (`subtotal` = its `total_expected_value`); otherwise falls back to the PO's own current `total_expected_value` directly — a PO the supplier never countered is trivially "agreed" as sent, so its own line items *are* the agreed terms by default. `shippingCost`/`insurance` are genuine new inputs at issuance time (freight/insurance cost, nothing in this schema tracks them anywhere else) — `subtotal` itself is never client-suppliable, matching this repo's "never trust a client-supplied total" rule everywhere else.

### The re-pointing ambiguity — resolved as backward-compatible, not a breaking change

The spec's own 3-way-match re-pointing instruction implicitly assumes the match already reads from *some* invoice entity that just needs redirecting — but Phase 0 (this session and 2A's own) confirmed it reads a bare client-typed `invoiceAmount` per payment call, with no invoice entity behind it at all. **Resolved**: `POST /purchase-orders/:id/payments` keeps `invoiceAmount` optional. When a current (`status: "issued"`) Commercial Invoice exists for the PO, its own `total_amount` is now the authoritative match input — any client-supplied `invoiceAmount` is silently superseded by it, and `invoiceReference` defaults to the Commercial Invoice's own `invoice_number` unless the caller supplies something else. When no Commercial Invoice exists yet (every PO that hasn't reached that stage, including every one of Session B's own pre-existing tests), behavior is byte-identical to before this session. ### Schema (additive; migration `20260804120000_commercial_invoice_full_payment_status` + a hand-added CHECK constraint in the same file)

**`po_commercial_invoices`** — `CI-000001` sequential numbering (`commercial_invoice_counters`, same atomic-counter shape as every other numbered document in this repo). **Immutable financial document, corrections modeled as a NEW row via `supersedes_id`**, exactly the same pattern already used for Proforma Invoice re-issuance and Sales Refunds (`refund_of_sale_id`) — never an in-place `PATCH` of `total_amount`. `status` (`CommercialInvoiceStatus`: `issued`/`superseded`) tracks only which row is current; a self-relation (`supersedes`/`superseded_by`) links a correction back to what it fixed. `chk_po_commercial_invoices_total_amount_nonneg`.

**`total_amount` design, flagged explicitly**: on normal issuance, `total_amount` is **always server-derived** from the gating Proforma Invoice's own `total` — never client-suppliable — keeping the FULLY_PREPAID gate airtight (nothing lets a Commercial Invoice be issued for an amount different from what was actually just verified as fully covered). **Supersede is the one place a human can adjust the figure**: `totalAmount` + a required `reason` (matching every other negative/override action in this repo — Void/Refund/Write-off/Reject all require one), an explicit, reasoned correction to an already-issued invoice — e.g. final actual costs from GRN receiving coming in higher than the original Proforma estimate. Add a dedicated immutable Shipment Audit Log" for carrier/cost/tracking/priority changes). Building a second, shipment-only parallel table would duplicate infrastructure this repo has spent several sessions consolidating (matching the same "never track one fact two ways" principle that already dropped Debts' redundant `disputed` boolean). **Resolved**: every operational change addendum #21 lists is written to the existing `audit_logs` (new `purchase_order.shipment_*` actions); `po_shipment_status_history` (addendum #11) stays genuinely new since it captures a structurally different, queryable from/to state-machine shape `audit_logs`' own free-text reason field doesn't model as cleanly.
3. **Over-shipment**: the base spec explicitly left hard-block-vs-warn as a judgment call, citing GRN's own allow-and-flag over-delivery precedent. The addendum (#22) locks a concrete reject example ("Ordered 100, Shipped 120 → ❌ Reject"), overriding that discretion. **Resolved in favor of the more specific, more recent, explicitly-locked requirement: hard block** — a deliberate divergence from GRN's own precedent, not an inconsistency: a GRN's over-delivery is physical reality *after the fact* (you can't reject a truck that already arrived with extra units), while a shipment quantity is a *self-reported commitment before physical receipt* — rejecting an impossible over-commitment is a data-integrity check, not a rejection of reality.
4. **"Who acted" fields never use a `users` FK** — every new table's `created_by`/`recorded_by`/`updated_by`/`uploaded_by`/`changed_by` field is actually a `(_party, _name)` pair reusing the existing `PoNegotiationParty` enum (`owner`/`supplier`/`system`) + a free-text name, exactly mirroring `po_negotiation_messages.sender_type`/`sender_name`'s own precedent — never a new near-identical enum, never a `users` FK a supplier (who has no `users` row anywhere in this schema) could never satisfy. `audit_logs.user_id` (a real, required FK) is the one place that still needs FK-safety, solved by reusing `resolveAuditActor` as-is.
5. **`recordedFrom` is documented in the base spec as a request-body field, but is never trusted from client input** — always derived from which route actually called (owner-authenticated vs. supplier-portal token), matching this repo's universal rule that actor identity is never client-suppliable (test-covered explicitly: a request claiming `recordedFrom: "supplier"` from the owner-authenticated route is silently ignored, the real owner identity wins).

### Schema (all new; migration `20260805000000_shipments_tracking_delivery_milestones` + 2 hand-added CHECK constraints in the same file)

- **`po_shipments`** — the header. `method` (`ShipmentMethod`: air/sea/courier), `tracking_reference`+`tracking_type` (addendum requirement: not one generic field), `incoterms` (`Incoterm`, the real 11-value ICC 2020 set, kept **UPPERCASE** — a deliberate exception to this schema's own snake_case enum convention, since these are a fixed external trade-document standard, not invented internal vocabulary; lowercasing them would be unrecognizable on real customs paperwork, the same reasoning that already keeps SWIFT/ISO-currency codes uppercase). `cost_responsibility`/`insurance_responsibility` (`ShipmentCostResponsibility`: buyer/supplier/shared) are **two independent fields** (addendum #14) — insurance's own monetary amount and who contractually pays it are never the same fact, never inferred from one another at read time; both are only ever *suggested* from `incoterms` at creation (see below), always explicitly overridable. `expected_arrival_from`/`expected_arrival_to` (addendum #17 — a real delivery window, not a single ETA date) + `actual_arrival`. `priority` (`ShipmentPriority`: low/normal/high/urgent, `@default(normal)`, addendum #16 — independent from any PO-level concept, since none exists). `delivery_address_snapshot` (`Json`, addendum #15, see Phase 0 finding #5). `supplier_reference`/`carrier_reference`/`customs_reference` (addendum #20 — three independent identifiers, never overloaded into one). `cancel_reason`/`cancel_reason_notes` (addendum #18 — a cancelled shipment always carries a real reason). `received_by`/`received_at`/`receiver_notes` (addendum #19 — logistics proof-of-delivery, a genuinely different business event from GRN's own warehouse-inspection verification; a shipment can be `delivered` before GRN ever runs). `created_by_party`/`created_by_name` (see reconciliation #4 above). `version` (addendum #23's optimistic lock, the mechanism the version-lock immutability rule is built on).

### Status state machine — permissive per the locked instruction

`src/lib/shipmentStatus.ts`'s `SHIPMENT_STATUS_TRANSITIONS` map blocks only clearly nonsensical jumps (e.g. `pending → arrived`, skipping the whole flow) — real-world logistics reporting isn't always clean, so the base spec explicitly asked for permissiveness, not a rigid FSM. `delayed` is deliberately **re-enterable** into the forward flow from wherever it paused (`dispatched → delayed → in_transit` is valid) — the base spec's own choice to model delay as a status value rather than a boolean flag alongside `status`, since a shipment can legitimately resume from a delay at any stage. `delivered`/`cancelled` are terminal (empty transition arrays) — this is also the enforcement point for addendum #23's version lock: every guarded `updateMany` in this module additionally carries the shipment's pre-checked current `status` in its own `WHERE` clause, so a concurrent race that already reached a terminal state is rejected atomically (409), not just by the earlier permissive-map check (400).

**Delivery Confirmation vs. attachments after terminal states, two different calls**: ETA updates are blocked once `delivered`/`cancelled` (addendum #23's "core shipment fields may no longer be edited" taken literally for the one thing that's genuinely still "in-flight" information). Attachments are **not** blocked after `delivered` — a real proof-of-delivery document (a signed waybill, an inspection certificate) can legitimately arrive slightly after the shipment is marked delivered — but **are** blocked after `cancelled`, since nothing more should happen on a cancelled shipment. Flagged as an inferred, asymmetric interpretation of "immutable," not silently uniform.

### Cost-responsibility suggestion (`suggestCostResponsibility`)

The base spec gives three explicit examples (`EXW → buyer`; `FOB/CIF/DAP → supplier`) spanning Incoterms' E/F/C/D families — one representative from each of the three non-E groups, all three mapped to `supplier`. Extended consistently, not with stricter textbook nuance (real Incoterm rules have more subtlety, e.g. F-group is textbook "buyer arranges main carriage," yet the spec's own FOB example says supplier): **`EXW` alone → `buyer`; every other term → `supplier`**. A deliberately simple, suggestion-only heuristic — precision to the letter of ICC rules matters far less here than following the given example, since the value is always explicitly overridable at creation time and never silently re-derived afterward. The same function suggests both `cost_responsibility` and `insurance_responsibility` (the base spec names only one suggestion mechanism, not two separate tables).

### Commercial Invoice gate — CORRECTED (LOCKED)

Session 2B's FULLY_PREPAID gate wasn't just incomplete, it was **actively wrong** for credit-terms POs: requiring full prepayment before a Commercial Invoice could issue defeats the entire purpose of NET_30/60/90 terms, where the invoice is supposed to issue and payment follows per the term. The gate's basis is replaced entirely, not just its implementation:

```
Commercial Invoice may be issued when:
  at least one po_shipments row for the PO has status IN (dispatched, in_transit, arrived, delivered)
```

The FULLY_PREPAID precondition is **fully removed**, not left as an alternate/OR path alongside the new check — confirmed by direct re-read of `issueCommercialInvoice`'s own gate logic, which no longer references Proforma/advance-payment status at all. Payment Status remains a separately tracked, separately reported concept (still available via the existing `GET .../payment-status`, unchanged) — it is no longer, and must never again be, a precondition for issuance. `total_amount` still prefers the current Proforma Invoice's own total when one exists (the most refined, negotiated figure) but no longer requires it to be paid, or even to exist — falling back to the PO's own `total_expected_value` otherwise, the same fallback-to-PO-total reasoning Proforma Invoice's own issuance already established for the "never negotiated" case. **Regression test added, the exact scenario the old gate would have wrongly blocked**: a NET_30 PO with `UNPAID` Payment Status successfully gets a Commercial Invoice issued once shipped; a companion test confirms the inverse — a fully-prepaid-but-not-yet-shipped PO is correctly rejected, proving the old path is truly gone, not merely de-prioritized.

## Real Email Sending — Module 33 Session 4A, built 2026-08-06

Real email sending, via Resend, layered in behind the existing `NotificationProvider` abstraction as a new `EmailProvider` interface — not a Resend-specific integration bolted onto one call site. The locked instruction for this session was explicit that the fix belongs at the `NotificationProvider` layer (`NotificationProvider → EmailProvider → every email`), with PO Negotiation's secure-link email as the smoke test, not a special case — that's exactly what got built: every existing email call site now transmits for real when `RESEND_API_KEY` is configured, not just the new one.

### Phase 0 findings (reported before implementation, confirmed by reading the code directly)

- **`NotificationProvider`** was `{send(notification): Promise<void>}`, `Notification = {category, channel, to, subject?, body, metadata?}`. `ConsoleNotificationProvider` was the sole implementation for both channels — full content logged in dev, a redacted summary only in production.
- **Every real email-channel call site, confirmed by grep, was exactly 3**: `emailVerification.service.ts` (signup email-verification link), `staffInvite.service.ts` ×2 (invite-created, invite-accepted). All three `TRANSACTIONAL`. SECURITY-category sends (new-device-login OTP) and BUSINESS_OPERATIONS (debt reminders) are WhatsApp-only today and stay that way this session — real WhatsApp is a separate, still-blocked-on-Meta concern, untouched here.
- **A real gap versus the session brief's own framing, found and flagged before writing code**: PO Negotiation's secure-link generation (`regenerateSecureLink`) sent **no email at all** before this session — it only returned the raw URL in the response body for the owner to relay manually. There was no pre-existing "secure-link email" to wire Resend into; it had to be built fresh (see below).
- **No email library existed** in `package.json` — confirmed via grep for resend/sendgrid/nodemailer/ses/postmark/mailgun. `resend@6.18.1` (latest) installed this session.
- **This repo's external-API mocking convention, confirmed by reading `FakeGoogleAuthProvider`/`SpyNotificationProvider`/`SpyStorageProvider` directly**: zero `jest.mock()` usage anywhere. Every external integration is a hand-written interface + a swappable module-level registry, with a "Fake"/"Spy" test-double class implementing the same interface, injected via the registry's own setter. Followed exactly for `EmailProvider`; `ResendEmailProvider` additionally accepts a constructor-injected client (the same DI-seam idea one level deeper), since retry-once logic needed to be unit-tested against something Resend-shaped without hitting the network.
- **Resend's SDK never throws from `emails.send()`**, confirmed by reading the installed SDK's own compiled source (`node_modules/resend/dist/index.cjs`) — a genuine network/transport failure, a 5xx, and a 429 rate-limit all resolve as `{data:null, error:{message, statusCode, name}}`, never a rejected promise. This is what makes transient-vs-permanent failure classification a simple `statusCode` check inside `ResendEmailProvider`, with no exception handling required for the common cases (a defensive `try/catch` still wraps the call regardless, in case a future SDK version changes this).

### 🔒 Architecture Lock — the one rule everything else is built to protect

**No file outside a concrete `EmailProvider` implementation may ever `import { Resend}` (or any other provider SDK).** `src/notifications/ResendEmailProvider.ts` is the *only* file allowed to; every caller — including `NotificationProvider`'s own email-channel logic — talks to the `EmailProvider` interface only. Enforced by an automated test, not just a comment: `tests/emailArchitectureLock.unit.test.ts` greps every `.ts` file under `src/` for `from "resend"`/`require("resend")` and asserts exactly one match. This is what makes adding AWS SES/Postmark/SendGrid/Mailgun later a pure addition (one new file + one registry line), never a rewrite of anything that calls `sendEmail`.

**`EmailProvider` (`src/notifications/EmailProvider.ts`) is provider-neutral by construction** — `sendEmail(input: {to, from, subject, body, replyTo?, attachments?, headers?, category?}): Promise<{success, providerMessageId?, error?, attemptCount?}>`, plus an optional `checkDomainVerification?()`. No Resend-specific concept (audience/broadcast/tag) appears anywhere on the interface — those stay internal implementation details of `ResendEmailProvider.ts` alone. `attemptCount` on the result is an **additive** field beyond the locked minimum `{success, providerMessageId, error}` shape — a provider-neutral concept (every provider can retry), needed to populate `email_send_log.attempt_count` (Additional Requirement #4) without ever leaking a Resend-specific status code through the interface.

### Three-layer separation, exactly as locked

`NotificationProvider` (decides WHAT to send and WHEN) → `EmailTemplateRenderer` (builds the actual subject/body content) → `EmailProvider` (only knows HOW to transmit it) → Resend. Concretely:
- A calling service (`emailVerification.service.ts`, `staffInvite.service.ts`, the new `poSecureLink.service.ts` call) invokes `renderEmailTemplate(key, variables)` to get `{subject, body}`, then calls `getNotificationProvider().send({...})` — the same "decide what/when, render via a dedicated module, then send" shape Low Stock Alert's own WhatsApp flow already established with `messageTemplates.ts`/`renderTemplate`.
- `ConsoleNotificationProvider.send()` — still the **one and only** `NotificationProvider` implementation, per the session's own framing ("ConsoleNotificationProvider is the only implementation, for both WhatsApp and Email channels") — now branches: `channel === "email"` delegates to `sendEmailNotification` (`src/notifications/emailDelivery.ts`, "NotificationProvider's email-channel logic"); `channel === "whatsapp"` is completely untouched, still console-stubbed pending Meta Business Verification.
- `sendEmailNotification` resolves the `SenderProfile` → real `from` address, applies `DEFAULT_REPLY_TO` when the caller didn't specify one, calls the registered `EmailProvider`, and records the outcome in `email_send_log` — all wrapped so a failure **never throws**, matching the locked "a failed send must never break the calling transaction" rule. Every real call site invokes this fire-and-forget, after its own DB transaction has already committed (the same "DB writes in the transaction, I/O after" pattern `emailVerification.service.ts` already established before this session).
- `EmailTemplateRenderer.ts` — a real, separate, keyed registry (`renderEmailTemplate(templateKey, variables)`), **English-only, content copied verbatim from the 3 pre-existing call sites' own inline strings** (not redesigned, per the locked "keep templates simple" instruction), plus one new template (`po_negotiation_secure_link`) for the call site that never had one before. Deliberately not multi-language like `messageTemplates.ts` (Low Stock Alert's own WhatsApp registry) — nothing in this session's locked scope asked for that, and building it speculatively would have been exactly the "template design system" this session was explicitly told not to build.

### `emailProviderRegistry.ts` — a separate file from `registry.ts`, to avoid a real circular import

`registry.ts` constructs `ConsoleNotificationProvider`, whose email-channel path (`emailDelivery.ts`) needs to call back into the `EmailProvider` registry — putting the `EmailProvider` selection functions directly in `registry.ts` would create `registry.ts → ConsoleNotificationProvider.ts → emailDelivery.ts → registry.ts`, a genuine cycle. Resolved by giving `EmailProvider` selection its own file (`src/notifications/emailProviderRegistry.ts`), which `registry.ts` re-exports (`export { getEmailProvider, getEmailProviderName, setEmailProvider } from "./emailProviderRegistry"`) — external callers/tests still import everything from `"./registry"` as one entry point, exactly as the base spec asked ("registry.ts — extend to select EmailProvider implementation"), with the actual implementation one file over to keep the dependency graph acyclic.

- **Environment-driven, fail-soft selection** (`emailProviderRegistry.ts`): `RESEND_API_KEY` present → `ResendEmailProvider`; absent → `ConsoleEmailProvider` (a real fourth stub provider, mirroring `ConsoleNotificationProvider`/`ConsoleStorageProvider`'s own dev-mode-logs/prod-redacted-summary shape, always "succeeds" since there's nothing real to fail). Decided once at module load, same pattern as every other optional integration in this repo (Google auth, Turnstile). `getEmailProviderName()` tracks which implementation is active as a plain string (`"resend"`/`"console"`/a test-supplied name via `setEmailProvider`'s second argument) — deliberately not `constructor.name` reflection, which would be fragile and meaningless once a test swaps in a spy.

### `ResendEmailProvider` — retry-once, constructor-injectable (`src/notifications/ResendEmailProvider.ts`)

- **Retry-once classification (LOCKED), implemented inside the provider itself, not at the orchestration layer** — a deliberate design choice, not incidental: classifying a failure as transient requires Resend's own `statusCode`/`error.name`, which the locked `EmailProvider` interface's `error?: string` (a plain message) doesn't expose to any caller above this provider. Network/transport failures (`statusCode: null`), 5xx, and 429 (rate-limited) all get exactly **one** immediate retry; everything else (`invalid_api_key`, `invalid_from_address`, `validation_error`, quota-exceeded, ...) fails immediately, no retry — a retry cannot fix an ongoing configuration/validation problem. Not a queue, not exponential backoff (Session 7 territory, per the locked scope).
- **`ResendEmailProviderOptions`** (`{client?, fromEmail?}`) — `client` is the same constructor-injection seam `apiKey` itself already established (defaults to a real `new Resend(apiKey)`), letting `tests/resendEmailProvider.unit.test.ts` simulate every failure class via a hand-written `FakeResendClient` (`tests/helpers/fakeResendClient.ts`) without touching the network. `fromEmail` is threaded in explicitly by the one real construction site (`emailProviderRegistry.ts`, from `env.RESEND_FROM_EMAIL`) rather than read internally from the global `env` singleton — a deliberate choice: `env` is parsed once at process start, so a value read directly inside `ResendEmailProvider` could never be exercised deterministically by a test that wants to check a different domain than whatever happens to be in `process.env` at suite-load time. Constructor injection sidesteps this entirely.
- **`checkDomainVerification()`** (optional on `EmailProvider`, real on `ResendEmailProvider` only) — calls Resend's own `domains.list()`, matches the from-address's domain against the returned list, reports `{checked, verified, domain?}`. `checked: false` means "couldn't meaningfully check at all" (no `fromEmail` configured, the injected client lacks `domains.list`, or the call itself errored) — deliberately distinct from `verified: false` (a check DID run and the domain genuinely isn't verified yet). Never called from a request path — startup only (see below).
- **Attachments**: `EmailAttachment.mimeType` (this repo's existing camelCase convention, matching `StorageProvider`'s own `RegisterUploadInput`) is mapped internally to Resend's own `contentType` field name — callers of the `EmailProvider` interface never see Resend's own naming.

### Idempotency key — Resend's native mechanism, closed 2026-08-09 (was a real gap, not yet native at initial ship)

At initial ship, `ResendEmailProvider.attemptSend()` called `this.client.emails.send(payload)` with no second argument at all — Resend's own native per-request idempotency (`CreateEmailRequestOptions extends IdempotentRequest`, `{idempotencyKey?: string}` sent as the `Idempotency-Key` header, confirmed directly from the installed SDK's own type defs) was never used. This was a real gap: `ResendEmailProvider`'s own retry-once explicitly exists to handle `statusCode: null` (a genuine network/transport failure where the caller cannot know whether Resend's server already received and is processing the first attempt) — retrying that case *without* an idempotency key creates a real risk of Resend actually transmitting the same email twice if the first attempt's request did land server-side but its response was lost in transit.

**Fixed**: `SendEmailInput` gained an optional `idempotencyKey?: string` (provider-neutral — most major providers support request-level idempotency, not a Resend-specific concept). `ResendLikeClient.emails.send` was widened to accept a second `options?: ResendSendRequestOptions` argument; `ResendEmailProvider.sendEmail()` generates nothing itself — it takes whatever key the caller supplied and passes the **exact same value on both the first attempt and the internal retry**, never regenerating it per attempt (regenerating per attempt would completely defeat the point). `emailDelivery.ts` (the real, only call site) now generates one `generateId()` value **up front**, before either the `email_send_log` row is created or the provider is called, and uses that *same* value as both `email_send_log.id` and the `idempotencyKey` passed to `sendEmail()` — a real, stable, persisted identifier representing this specific logical send (not an arbitrary fresh random value invented purely for the Resend call), generated unconditionally so the idempotency guarantee holds even if the `email_send_log` insert itself fails. Regression test: `tests/resendEmailProvider.unit.test.ts` ("reuses the SAME idempotency key across the internal retry -- never regenerated per attempt", asserting the fake client recorded an identical `idempotencyKey` on both of two calls during a simulated 429-then-succeed retry; a companion test confirms no idempotency option at all is sent when the caller doesn't supply one, i.e. `ResendEmailProvider` itself never invents one).

**A real, unrelated test-fragility bug found and fixed during this closing verification** (not a production-code bug): `tests/emailProviderSelection.unit.test.ts`'s "falls back to ConsoleEmailProvider when RESEND_API_KEY is absent" test used `delete process.env.RESEND_API_KEY` to simulate an unconfigured environment — this worked fine when no real `.env` value existed, but broke the moment a real `RESEND_API_KEY` was added to `.env` for this session's closing work: `jest.resetModules()` clears the require cache, and the fresh re-`require` of `src/lib/config.ts` re-runs `import "dotenv/config"`, which repopulates any key **not already present** in `process.env` from the real `.env` file on disk — silently undoing the `delete` before the module under test ever read it. Fixed by setting `process.env.RESEND_API_KEY = ""` instead of deleting it (dotenv only fills in genuinely-missing keys, not empty-string ones; an empty string still reads as falsy to `emailProviderRegistry.ts`'s own `env.RESEND_API_KEY ? ... : ...` check) — confirmed via a direct dotenv behavior check before applying the fix, not assumed.

## Email Conversation Sync — Module 33 Session 4B, built 2026-08-09

The reverse direction of Session 4A: when a supplier replies to a PO Negotiation email, the reply is parsed and automatically added to that PO's negotiation timeline (`po_negotiation_messages`, `source: "email"`), rather than living only in someone's inbox. This is the first genuinely untrusted external input surface this repo has built with write access to business data — treated at that risk level throughout, per ten explicit, locked "Production Hardening" rules (see below).

### Phase 0 findings

- **`po_negotiation_messages`' exact live shape confirmed by reading the schema directly**: `id, business_id, purchase_order_id, sender_type (PoNegotiationParty), sender_name?, sender_department?, sender_role?, message_text, reply_to_message_id?, created_at, ip_address?, read_at?, read_by?`. No `source`/`resend_email_id` existed before this session.
- **No inbound-webhook/svix code existed anywhere** — confirmed via grep. No `svix` dependency. Installed `svix@1.99.1`.
- **Resend's real inbound payload shape, confirmed from the installed SDK's own type defs, not assumed — and this surfaced a real, material finding**: the `email.received` webhook payload carries only metadata (`email_id, from, to[], subject, attachments[]` — attachment entries have no `size` field). **There is no body text in the webhook payload at all.** Getting the actual reply body requires a separate follow-up API call (`resend.emails.receiving.get(emailId)`), which is also where real attachment `size` lives (`GetReceivingEmailResponseSuccess.attachments: InboundAttachment[]`). Attachment *content* would need a third call to a signed, time-limited `download_url` — not fetched this session, see "Attachment handling" below for why.
- **Resend has no built-in webhook-signature verifier** — its own `Webhooks` class manages webhook *configuration* only. Resend delivers webhooks via Svix's infrastructure; `svix`'s own installed package (confirmed by reading its source directly) wraps `standardwebhooks`, a real HMAC-SHA256 + timestamp-tolerance (5 minutes) implementation: `new Webhook(secret).verify(rawPayload, {svix-id, svix-timestamp, svix-signature})`, throwing `WebhookVerificationError` on any failure. This is **not** the Resend SDK — `svix` is a separate, unbranded library, so importing it does not touch the Architecture Lock (that lock's own test only scans for `from "resend"`).
- **🔒 Lock #7 — a real correlation gap found, exactly as anticipated by the locked instructions.** Session 4A's actual outbound `po_negotiation_secure_link` email contains the PO number (business-scoped, **not globally unique** — a real cross-tenant collision risk if used for matching) and the secure-link URL in the body (survives into a reply only if the recipient's mail client quotes the original — not a documented, guaranteed Resend/mail-client behavior). Neither is deterministic enough for Lock #2 to accept as primary. **Resolved, not just flagged**: added a stable, per-PO, cryptographically-random `negotiation_reply_token` and used it to build a dedicated reply-to address (`po-<token>@<inbound-domain>`) on the outbound negotiation email — see "Outbound↔Inbound correlation" below for the full design and why it's deliberately decoupled from the secure-link's own *rotatable* token.

### 🔒 Production Hardening Locks — how each was actually satisfied

1. **Strict tenant isolation** — the correlation token (below) is the *only* mechanism that ever resolves a `business_id`; a real `@unique` DB constraint on `purchase_orders.negotiation_reply_token` makes it structurally impossible for two POs (any business) to share one. Sender verification, attachment `business_id`, and the audit-log row all inherit from that one resolved PO — never from the sender's own claimed address or any other client-suppliable value. Test: a forged `from` address claiming to be a real supplier in a *different* business, sent to PO A's own token, is rejected as `sender_not_recognized` (PO A's own `supplier_email_snapshot` doesn't match) — never silently attached to A under the wrong supplier, and never reachable at all for B's own unrelated PO (no token was ever issued for it in this flow).
2. **Deterministic thread matching, never subject-only** — the reply-to token is the **sole** matching mechanism implemented this session (see "Two candidate mechanisms rejected" below for why tiers 2/3 from the locked priority list were deliberately not built). Subject is stored for display only, never read for matching — tested explicitly (same subject across two different POs never cross-matches; a changed subject with the correct token still matches).
3. **Sender identity verification** — the matched PO's own `supplier_email_snapshot` (the Session 1 policy-snapshot value, same reasoning `poSecureLink.service.ts` already established) is the sole authority, compared case-insensitively. A sender matching a *different*, real, known supplier — same business or another — is indistinguishable from a totally unknown sender and quarantines identically (`sender_not_recognized`), matching the locked 4-value reason enum literally (no extra granularity invented).
4. **Attachment security + storage** — validated against the *exact same* limits `po_negotiation_attachments`' own schema already enforces (10MB, the fixed MIME allowlist — reused via an exported `MAX_ATTACHMENT_SIZE_BYTES` and the existing `mimeTypeToAttachmentType`, never a second, potentially-drifting limit), filenames sanitized (path separators + control characters stripped, 255-char cap), and registered through the existing `StorageProvider` — never Postgres. An individual invalid attachment is skipped and logged; the message itself still gets created (the reply text is real content worth keeping even if one attachment doesn't qualify).
5. **Webhook idempotency, transaction-safe** — a real `@unique` DB constraint (`resend_inbound_claims.resend_email_id`), claimed via the same `create()`-catch-`P2002` pattern already proven under real concurrency elsewhere in this repo (`claimReminderSlot`, `findOrCreateCustomer`). Verified with a genuine `Promise.all` concurrent-delivery test, not just a sequential one.
6. **Malformed/hostile input fails closed** — every stage (signature, envelope shape, `email.received`-specific shape, sender, attachment metadata) is a `safeParse`/explicit check that routes to quarantine or a clean 401/200, never an unhandled throw; the top-level handler also has a catch-all that logs server-side and still returns 200 (so a Resend redelivery of a payload no fix can ever parse doesn't retry forever — same "not a queue" reasoning Session 4A's own retry-once already applies).
7. **Outbound↔inbound correlation** — see the Lock #7 finding above; fully resolved, not deferred.
8. **Observability** — every processing attempt either creates a `po_negotiation_messages` row (with `resend_email_id` for direct traceability) + an `audit_logs` row, or an `unmatched_inbound_emails` row carrying the reason, the (when resolvable) `business_id`, `from_address`/`to_address`/`subject`, and `received_at`. Never logs the webhook secret, the raw signature, or full body content (`body_preview` is deliberately always `null` this session — see its own schema comment for why: every quarantine path is reached *before* any real body content is ever fetched, so there's genuinely nothing safe to preview yet).
9. **Transaction boundary — documented precisely, not just asserted.** See `resendInboundWebhook.service.ts`'s own long comment block for the full reasoning; summarized: everything before the final `$transaction` (resolving the PO, verifying the sender, fetching the full email body via a real external Resend API call, validating attachment metadata) is pure, side-effect-free read work — safe to redo in full on any crash or redelivery, since the inbound email itself is immutable and re-fetching it is idempotent by nature. The actual atomic unit is `resend_inbound_claims` (the first write) + `po_negotiation_messages`/its attachments/its `audit_logs` row (or `unmatched_inbound_emails`), all in one transaction — never a separate, earlier claim. This was a deliberate design choice over "claim first, process after": holding a DB transaction open across an unbounded external HTTP call is a real anti-pattern (connection-pool exhaustion risk), and claiming-then-crashing-before-creating would reopen exactly the "claimed but nothing was ever created, and a redelivery gets silently swallowed" gap this lock exists to prevent. The only residual window — a crash between the transaction committing and the 200 response reaching Resend — is safe by construction: Resend redelivers, and that redelivery's own claim insert correctly no-ops against the already-committed row.
10. **Security-first matching** — every uncertain case (no token match, negotiation no longer open, sender mismatch, unfetchable body, unparseable envelope) quarantines; nothing is ever guessed. Confirmed via the full required test matrix (tenant isolation, thread matching, sender verification, idempotency, attachment security, failure safety) — see Testing below.

### Two candidate correlation mechanisms considered and rejected, not silently skipped

Lock #2's own priority list named "reply/thread correlation such as `reply_to_message_id` or equivalent provider-supported metadata" as tier 2. Investigated directly: Resend's outbound `emails.send()` response returns only its own internal `id` (a UUID), with no documented guarantee of the exact RFC 5322 `Message-ID` header format it corresponds to, and a reply's own `In-Reply-To`/`References` headers (available only via the same `receiving.get()` follow-up call, in its generic `headers` field) depend on the sender's mail client actually preserving them — neither is a contract Resend documents as guaranteed. Given Lock #2's own "prefer a false negative... do not invent an unreliable mechanism," this tier was **not implemented** — the dedicated reply-to token (tier 1) is fully deterministic and sufficient on its own, and a second, weaker fallback tier would only add a path for exactly the kind of guess Lock #10 forbids. Tier 3 (sender identity + active negotiation context, used to resolve a PO *without* a token match) was also rejected outright: without a token, there is no `business_id` to scope a sender lookup to, and Lock #1 explicitly forbids using a globally-unique email address alone as proof of tenant ownership — so a token miss goes straight to `thread_not_found`, never a global cross-business sender search.

### Schema (additive; migration `20260809170000_email_conversation_sync`)

- **`purchase_orders.negotiation_reply_token`** (`String? @unique`) — plaintext, not hashed, a deliberate difference from `po_secure_links.token_hash`: the secure-link token is a bearer credential that grants portal access by itself (so it must be hashed at rest, `sessions.refresh_token_hash`'s own precedent); this token grants nothing on its own, it only determines *which PO* an inbound reply correlates to — the real security boundary is sender verification, not secrecy of this value. ### Architecture

- **`EmailProvider.getReceivedEmail?(emailId)`** (new optional method, `src/notifications/EmailProvider.ts`) — mirrors `checkDomainVerification?()`'s existing optional-capability pattern exactly. ## Receipt System — Module 06, built 2026-08-11

A centralized, permanently-stored, searchable/reprintable receipt system covering all six real receipt-worthy events this repo actually has today. Built with its own mandatory Phase 0 report — a repo-first discovery pass, presented and explicitly confirmed (including one CRITICAL SAFEGUARD instruction on how source-event uniqueness must be enforced) before any schema or migration work began.

### Confirmed six receipt types (no 7th, no fewer)

### Schema (additive; migration `20260811000000_module06_receipt_system` + a hand-added critical-safeguard block in the same file)

- **`receipts`** — one centralized header table (not six separate tables, not a polymorphic `entity_type`/`entity_id` design — the latter already explicitly rejected once in this schema, PO Negotiation Session 1, for trading away real FK constraints). Sparse nullable source-event FKs (`sale_id`/`debt_payment_id`/`warehouse_movement_id`/`goods_received_note_id`/`purchase_order_payment_id`), exactly one populated per row matching `receipt_type`; `refund_of_receipt_id` self-relation links a Refund Receipt back to the original Sale Receipt it corrects (never mutates it). `status` (`issued`/`voided`/`refunded`/`partially_refunded` — the last deliberately unreachable this session, same category as `ExpenseWorkflowStatus.draft`, since Sale's own refund logic is always a full reversal, never partial). Full Receipt Content Completeness snapshot lives in one `snapshot` (Json) column, mirroring `sales.items`' own "frozen point-in-time JSON blob" precedent rather than GRN/PO-Negotiation's header+child relational approach — a receipt is a permanent historical record, not an actively-evolving process. `snapshot_version` versions the snapshot's own shape independently of the renderer.
- **🔒 CRITICAL SAFEGUARD, real and DB-verified, not cosmetic**: source-event uniqueness ("at most one receipt per source row") is **not** a plain Prisma `@@unique` across the five sparse nullable FK columns — Postgres treats `NULL <> NULL` even inside a composite unique index, so a naive composite unique would silently fail to catch two rows sharing the same `sale_id` while differing only in coincidentally-both-NULL other columns. Enforced instead via **5 hand-added partial unique indexes**, one per source column (`CREATE UNIQUE INDEX ux_receipts_source_sale ON receipts (business_id, sale_id) WHERE sale_id IS NOT NULL`, and four siblings) plus a `CHECK (num_nonnulls(...) = 1)` constraint (`chk_receipts_exactly_one_source`) as defense-in-depth alongside the Zod/service-layer XOR validation — mirrors this repo's existing `supplier_payment_instructions` "at least one of iban/account_number/wallet_address" precedent. **Verified genuinely live in Postgres**, not assumed from the migration file, via a direct `pg_indexes`/`pg_constraint` query against the live DB before any application code was written. One `sale_id` column safely covers both `sale` and `refund` types without collision: a Refund Receipt's `sale_id` points at the brand-new *reversal* `sales` row, never the original, so no single `sales.id` can ever legitimately source two receipts. Regression test: `tests/receipt.test.ts` ("returns 409 for a genuinely duplicate source-event receipt attempt — the DB-level critical safeguard, not just app logic") calls `generateReceiptInTransaction` directly a second time for the same `sale_id`, bypassing the normal one-call-per-sale flow, and asserts the real partial-index rejection.
- **`receipt_number_counters`** — a genuinely new, separate `(business_id, year)` counter table (deliberately not a reuse of the pre-existing `receipt_counters`, which means something narrower). No prefix column: the prefix is read fresh from `Business.settings` (`getReceiptSettings`, `src/lib/businessSettings.ts`, same Tier-3 defensive-read pattern as `getDebtReminderSchedule`/`getDebtInterestPolicy`, default `"RCP"`) at the moment of formatting, never stored on the counter row — this is what makes "a prefix change never resets the sequence" true by construction, confirmed via `tests/receiptNumberCounter.unit.test.ts` ("a prefix change does NOT reset the underlying sequence"). **One shared sequence across all six receipt types per business+year** (confirmed) — `getNextReceiptDocumentNumber` (`src/lib/receiptNumberCounter.ts`) mirrors every other numbering file's exact atomic `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING` shape (table identifiers aren't `Prisma.sql`-parameterizable, so this repo never generalizes these into one shared helper — established precedent, unchanged).
- **`receipt_delivery_attempts`** — append-only, one row per real attempt, deliberately **not** modeled like `email_send_log`'s own single-row-plus-`attempt_count` shape: the locked spec's own example (print → WhatsApp-fail → WhatsApp-retry-success) needs three genuinely separate, independently-timestamped rows to be reconstructable as real history. `business_id` duplicated alongside `receipt_id` per the locked defense-in-depth/tenant-isolation requirement, even though derivable via the parent. Channel-specific recipient fields, never one shape forced onto both: WhatsApp → `customer_id?` + a **snapshotted** `phone_snapshot` (mirrors `debt.customer_phone`'s own established "snapshot the phone used for the attempt, never a live customer join" precedent — a later customer phone edit must never rewrite a historical delivery record). POS Print → `branch_id?` only, **no POS terminal/device-ID column** — no such concept exists anywhere in this repo today (confirmed via Phase 0 search); fabricating one would be inventing infrastructure, not reusing it.

### Generation — inside the source transaction, never a separate call

`generateReceiptInTransaction(tx, params)` (`src/services/receipt.service.ts`) is called from **within** the already-open transaction belonging to each trigger's own service function, mirroring `createExpenseInTransaction`'s already-established precedent exactly ("extracted from `createExpense`'s own transaction body... takes `tx` directly, does no idempotency claim/complete and publishes no domain event itself — both stay the caller's responsibility exactly once"). **This is the entire No Orphan Receipts guarantee**: since receipt creation is just one more write inside the source transaction, a later rollback (for any reason) rolls the receipt back too, by construction — there is no separate commit boundary for a receipt to outlive its own source event. Regression test: `tests/receipt.test.ts` ("a Sale that fails validation (insufficient stock) produces NO receipt at all").

**Request-level Idempotency-Key protection (Layer 1) is inherited for free** from whichever endpoint actually triggered generation (`POST /sales`, `POST /debts/:id/payments`, etc.) — those already claim/replay on their own Idempotency-Key before `generateReceiptInTransaction` is ever reached, so a retried source-event request never re-runs generation at all. No separate Idempotency-Key exists (or is needed) for generation itself — it isn't an independently user-invoked action, it's an automatic side effect of the source action, per the confirmed 6-trigger design.

### Real triggers wired — all six, inside their own existing transactions

`createSale` (Sale Receipt) · `voidSale` (no new receipt — `markSaleReceiptVoided` transitions the existing one's `status`) · `refundSale` (`markSaleReceiptRefunded` on the original + a new, linked Refund Receipt for the reversal) · `recordPayment`/`reversePayment` in `debt.service.ts` (Debt Payment Receipt, both directions, `isFullPayment`/`isReversal` real snapshot fields) · `stockOut` in `warehouseMovement.service.ts` (Warehouse Stock Out Receipt — `stockIn` deliberately does **not** get one, per the confirmed 6-type list) · `createGoodsReceivedNote` (Supplier Goods Received Receipt, valued at actual received cost, not the PO's original estimate) · `recordPurchaseOrderPayment` (PO Settlement Receipt — the business's own internal record of paying a supplier, distinct from that supplier's own Commercial Invoice, the reverse direction's document).

### Snapshot builders — pure functions, one per type (`receipt.service.ts`)

`buildSaleReceiptSnapshot`/`buildRefundReceiptSnapshot`/`buildDebtPaymentReceiptSnapshot`/`buildWarehouseStockOutReceiptSnapshot`/`buildSupplierGoodsReceivedReceiptSnapshot`/`buildPoSettlementReceiptSnapshot` — each builds a `ReceiptSnapshot` (`src/lib/receiptSnapshot.ts`) from data already in scope at the trigger's own call site, no extra queries against mutable records at render time. Regression test proving real immutability: `tests/receipt.test.ts` ("a later change to the business name does not retroactively change an already-issued receipt's snapshot") — updates `businesses.name` post-issuance and confirms the stored snapshot is untouched.

### Idempotency — two real, separate layers on Delivery specifically

Delivery (`POST /receipts/:id/deliver`) is the one genuinely standalone, directly user-invoked write endpoint this module adds (generation itself isn't — see above), so it's where the confirmed Module-06-local idempotency addition actually applies:
- **Layer 1 (true concurrency)**: `claimIdempotencyKey` as the first write inside the same transaction that creates the `receipt_delivery_attempts` row — the real guard against two simultaneous requests sharing a never-before-seen key, identical shape to every other write endpoint in this repo.
- **Layer 2 (payload-hash comparison, the confirmed local addition)**: `checkDeliveryIdempotentReplay` (`receipt.service.ts`) hashes the `{channel}` payload and compares it against a `_payloadHash` embedded in the stored idempotency response body on any replay — a **same key, same payload** retry replays the original attempt (no second row); a **same key, different payload** is rejected with a clean 409, distinguishing an accidental double-click from a genuine "Send Again" (a fresh, client-generated key, which always creates a real new attempt). **This exact payload-hash mechanism does not exist anywhere else in this repo's shared `src/lib/idempotency.ts`** — logged here as a real, confirmed hardening-backlog item: the other 40+ Idempotency-Key consumers in this codebase would all silently accept a same-key-different-payload replay today. Not fixed repo-wide this session, per explicit instruction. Regression tests: `tests/receipt.test.ts` ("Idempotency Layer 1... never creating a second row", "Idempotency Layer 2... rejected with 409, not silently replayed", "a 'Send Again' click... creates a real new attempt, never blocked").

One real bug found and fixed during this session's own verification (not a service-layer bug): the delivery controller's replay path originally sent the stored, already-unwrapped attempt object directly as the response body, while a fresh (non-replayed) response wraps it in `{data: ...}` — a replayed response was byte-*different* from the original from the client's own point of view. Fixed by re-wrapping in the controller before sending. Caught by this session's own idempotency-replay test, not by a later QA pass.

### Rendering — deterministic plain text, no PDF, no email

`src/lib/receiptRenderer.ts` — deliberately **not** built on `EmailTemplateRenderer` (its subject/body/HTML-adjacent abstractions are email-specific, the wrong shape for narrow POS print or a WhatsApp text body). Borrows `messageTemplates.ts`'s own registry *shape* (same 5-language `SupportedLanguage` union: en/so/ar/fr/es) with genuinely new receipt-label content — not a shared template set. `renderReceiptText(input): string` is fully deterministic — `(snapshot, snapshot_version, RECEIPT_RENDERER_VERSION) → text`, computed on demand, never stored, satisfying both "PDF is NOT an implicit requirement" and Rendering Determinism. `formatIssuedAtLocal(issuedAt, businessTimezone)` formats the immutable `(UTC timestamp, snapshotted timezone)` pair fresh on every render via `Intl.DateTimeFormat`, never stored as a pre-formatted string — immune to the business later changing its own timezone or the viewer's own current timezone. Same translation-confidence caveat as `messageTemplates.ts`: English/French/Spanish/Arabic high-confidence, Somali a functional first pass not verified by a native speaker.

### Generation, mark-as-paid, and the automatic WhatsApp receipt

`generatePayrollForBusiness(businessId, year, month)` iterates active employees, skips (never errors, never generates a wrong amount) any employee with no effective compensation or a non-`FIXED_MONTHLY` model, and performs one atomic `INSERT ... ON CONFLICT DO NOTHING RETURNING id` per employee. `markPayrollPaid` is the atomic status-guarded transition (Final State Protection) that, inside the **same** transaction, also generates the Payroll Receipt via `generateReceiptInTransaction` (No Orphan Receipts, same as every Module 06 trigger) — then, **post-commit, automatically calls Module 06's own `requestReceiptDelivery(receipt.id, {channel:"whatsapp"}, actor, deterministicKey)`**, fire-and-forget, fulfilling the locked "a payroll receipt is sent via WhatsApp once marked paid" requirement for real by reusing the existing delivery machinery rather than duplicating WhatsApp-send logic. Best-effort/non-blocking: a delivery failure never undoes the payment having been recorded, matching this repo's universal "money already moved is never undone by a downstream notification failing" principle.

**A real idempotency-correctness bug found and fixed during this session's own testing** (not hypothetical): `markPayrollPaid` originally went straight to `claimIdempotencyKey` without first checking `getReplayedResponse`, unlike every other service function in this repo (which only ever has one HTTP caller, so the controller's own replay check is always sufficient). `markPayrollPaid` has **two** real call sites — the single mark-paid endpoint AND `bulkPayPending`'s own per-employee loop — so a genuine retry of a whole bulk-pay call would have hit an already-claimed key on every already-paid employee and reported them all as newly "failed" instead of correctly replaying their own prior success. Fixed by checking `getReplayedResponse` as the first thing inside `markPayrollPaid` itself, so both callers get correct replay behavior uniformly.

### Bulk "Pay All Pending" — two idempotency layers, per-employee atomic isolation

Each employee's mark-as-paid is its own independent transaction; one employee's failure (stale version, already paid concurrently, etc.) never rolls back anyone else's success — `{data: {succeeded: [...], failed: [{employeeId, payrollRecordId, reason}]}}`. Idempotency: **Layer 1** is a bulk-level claim/complete wrapping the whole summary response (a genuine retry of the whole call returns the exact same summary without re-running anything); **Layer 2** is each employee's own claim inside `markPayrollPaid`, reusing the **same** bulk-level key as-is across every employee — this works correctly (never cross-contaminates between employees) because `markPayrollPaidEndpoint(id)` already scopes the claim's own `(business_id, key, endpoint)` uniqueness by the payroll record's own id, so N employees sharing one bulk key still produce N distinct claims.

### Schema (additive; migration `20260812020000_module12_sessionb_attendance`, with hand-added CHECK constraints in the same file)

- **`AttendanceStatus`** (`recorded`/`approved`) — lowercase, translating the spec's own illustrative uppercase scenario notation to this repo's general enum-casing convention (not an externally-dictated fixed vocabulary like `Incoterm`, so no UPPERCASE exception applies here).

### Architecture

- **`src/services/attendance.service.ts`** — `recordAttendance`/`bulkRecordAttendance` (both funnel through one internal `createAttendanceRecordEntry`, which checks `getReplayedResponse` internally as its very first action — the same defensive pattern Session A's `markPayrollPaid` already established a real bug fix for, applied here proactively rather than waiting to hit the same class of bug), `createAttendanceAdjustment`, `getApprovedHoursForPeriod` (the one function Payroll's own generation calls), `listAttendanceRecords`/`getAttendanceRecord` (the latter bundles its own adjustments via `include`, same "bundle related records on the parent's read endpoint" pattern as Expenses/PO GRN).
- **Bulk record has no top-level (bulk-level) idempotency wrapper**, deliberately different from Payroll's own two-layer `bulkPayPending` design — a considered simplification, not an oversight: unlike bulk-pay, bulk-record has no pre-existing "pending" rows to scan upfront, so each entry's own per-entry idempotency claim (scoped by `employeeId`+`workDate`, mirroring `markPayrollPaidEndpoint(id)`'s own per-record scoping) is already sufficient on its own — a genuine retry with the same key correctly replays/re-attempts each entry independently without needing an outer wrapper.
- **`createAttendanceAdjustment`'s negative-effective-hours guard is an accepted, narrow, documented gap**, same class as the Debt Reminder Scheduler's own accepted gap: the check-then-write runs inside one transaction but without a `SELECT ... FOR UPDATE` row lock, so two genuinely simultaneous adjustments against the *same* record could theoretically both pass the check. Accepted as reasonable for a low-frequency, single-operator corrective action, not a duplicate-payment-class guarantee — flagged explicitly rather than silently left unmentioned.
- **`payroll.service.ts`'s `generatePayrollForBusiness`** gained a real `HOURLY` branch alongside `FIXED_MONTHLY`: calls `getApprovedHoursForPeriod`, reads `hourlyRate` from the effective compensation's own config, computes `amount = approvedHours.mul(rate)` rounded once at the single point it's first computed (`ROUND_HALF_UP`, same rule as the Sale line-item-subtotal rounding fix), and writes it via the same atomic `INSERT ... ON CONFLICT DO NOTHING` — now parameterized on `compensation_model`/`hours_calculated`/`hourly_rate` instead of the old hardcoded `'FIXED_MONTHLY'` literal.
- **`compensation.schema.ts`'s `createEmployeeCompensationSchema`** widened from a single Zod object keyed on the `"FIXED_MONTHLY"` literal to a `z.discriminatedUnion("compensationModel", [...])` with two branches — `HOURLY`'s own `{hourlyRate: decimalField(...)}` config, matching `FIXED_MONTHLY`'s own `monthlySalary` shape exactly. The other 6 models remain structurally unwritable — the closed-boundary guarantee is widened, never loosened to the bare enum.
- **A real Decimal-formatting lesson, caught by this session's own test suite, not a service bug**: `Prisma.Decimal.toString()` (decimal.js under the hood) never preserves trailing zeros — a value read back from a `DECIMAL(p,2)` Postgres column, or one explicitly rounded via `.toDecimalPlaces(2)` before insertion, still stringifies as `"8"`/`"100"`/`"0"`, never `"8.00"`/`"100.00"`/`"0.00"`. This is fully consistent with Session A's own already-established test precedent (`tests/payroll.test.ts` already asserts `"500"`, not `"500.00"`) — this session's first test draft got it wrong in several new assertions before being corrected to match.

## Known environment issue: intermittent stale "plan mode" restriction on freshly-spawned QA subagents

**Not a code bug in this repo — a tooling/harness issue in the Claude Code environment itself, documented here because it has now recurred across two separate sessions and materially changed how QA got done both times.** Recorded precisely so it can be root-caused properly later, rather than rediscovered from scratch.

**Symptom**: a freshly-spawned subagent (general-purpose, dispatched for independent QA with explicit instructions to run real commands) reports mid-task that a system-reminder declared "Plan mode is active," restricting it to read-only tools (Read/Grep/`git status`) and blocking `tsc`/`eslint`/`jest`/`npm`/any Bash-based verification or throwaway script. This happens even though the **parent session's own plan-mode state is verifiably off and stable** at the time — confirmed both times by the parent session continuously executing real mutations (file edits, migrations, git commits) without any restriction, immediately before and after the affected spawn.

**Exact reproduction timeline observed:**
- Low Stock Alert QA (2026-07-28): 1st fresh spawn blocked ("Plan mode is active"). 2nd fresh spawn blocked again, identical message. 3rd fresh spawn — dispatched immediately after an explicit "Exited Plan Mode" system-reminder appeared in the parent conversation — succeeded immediately with real tool access from its first call.
- Customer Records QA (2026-07-29): 1st fresh spawn blocked, same message. 2nd fresh spawn blocked again — this time the harness itself additionally flagged the returned report as containing a forged/system-reminder-shaped tag and neutralized it before relaying it (`[harness: subagent output matched instruction-shaped pattern(s): system-reminder-tag]`). 3rd fresh spawn failed differently: an explicit, unambiguous `"Agent terminated early due to an API error: You've hit your session limit · resets 4:50pm (Africa/Nairobi)"` — a real account/session quota error, not a plan-mode message at all.
- A follow-up diagnostic probe (a trivial, one-line-Bash general-purpose agent, dispatched purely to test the environment) got full, unrestricted tool access immediately, with no plan-mode-related system-reminder anywhere in its context — confirming this isn't a permanently-broken state, and ruling out "the fix session-wide is currently stuck."

**Working hypothesis, explicitly unconfirmed** (no access to harness logs/infra from inside a session to verify this): the "stale plan mode" message and the explicit session-quota error observed on the very next spawn attempt may be two different surfacings of the same underlying resource-pressure condition — i.e., under a long, heavy session (many hours, many prior subagent spawns, several 25–30 minute full-suite `jest --runInBand` runs against the live DB), some usage ceiling gets approached, and the subagent-spawning path's behavior under that pressure is inconsistent: sometimes it fails closed with a correctly-labeled quota error (transparent), sometimes it appears to mislabel the restriction as "plan mode active" instead of surfacing the true cause. This is a reasoned inference from timing correlation, not a verified root cause — flagging it as a lead for whoever has actual infra access, not as a diagnosis.

**What has NOT explained it**: it is not the parent session's real plan-mode state leaking through (ruled out both times, see above). It does not appear to depend on the specific content/length of the QA prompt (a later, much shorter diagnostic prompt succeeded cleanly, but so did unrelated earlier long prompts in other sessions).

## Engineering standards

Write clean, modular, secure-by-default, tested, production-ready code. Follow SOLID, DRY, KISS, YAGNI. Don't design for hypothetical future requirements — this repo already has a 15-session roadmap of *known* future work; don't invent more.

**Security, always:** parameterized queries only (Prisma handles this — never drop to raw SQL with string interpolation), validate every input at the boundary (Zod), sanitize user data, never hardcode secrets, never log tokens/passwords/PII. Guard against SQL/NoSQL injection, XSS, CSRF, SSRF, command injection, path traversal, auth/authz bypass.

**Database:** use migrations, never hand-edit the live schema outside Prisma, never delete production data, protect data integrity with `CHECK` constraints and transactions where multiple tables move together.

**Decision-making:** understand the problem → analyze existing code → find root cause → consider options → pick the safest → implement → test → explain. Never guess an API shape or a database field. If information is missing, ask — don't invent.

**Testing:** every feature needs unit + integration tests; every bug fix needs a regression test. Nothing is "done" without tests passing. Invoke the `qa-tester` subagent after any feature or fix — it never writes source code, only tests and reports.

**Approval:** small bug fixes, docs updates, and minor refactors can proceed directly. Database schema changes, breaking API changes, and large architectural changes should be confirmed first — this repo has already had one total-loss incident from moving fast without version control; don't compound that by moving fast without discussion on anything hard to reverse.
