## Tech stack

- Backend: Node.js + Express 5, TypeScript (strict)
- Database: PostgreSQL via Neon (serverless) + Prisma ORM 7, connected through `@prisma/adapter-neon` (Prisma 7 requires a driver adapter — plain connection strings in `schema.prisma` no longer work; the URL lives in `prisma.config.ts` for CLI/migrate use, and the adapter is passed directly to the `PrismaClient` constructor at runtime)
- Auth: JWT access tokens (Bearer header) + httpOnly-cookie refresh tokens with rotation, Google OAuth (`google-auth-library`), bcryptjs for password hashing, `cookie-parser` for reading the refresh/CSRF cookies
- Country reference data: `world-countries` (currency, calling code) + `countries-and-timezones` (IANA timezone) — real npm packages, not hand-authored, since neither alone covers all three fields
- Validation: Zod (env validation belongs in `src/lib/config.ts`)
- Security middleware: Helmet, `cors` (env-driven allowlist via `CORS_ORIGINS`, `credentials: true` now that cookie-based auth exists — do not reintroduce an `origin: true` fallback outside dev, that combination is a real hole with credentialed cookies), `express-rate-limit`
- Testing: Jest + ts-jest + Supertest, run against the live Neon DB (no separate test DB exists — known risk; any test that creates data must clean up after itself, e.g. via a `cleanupTestBusiness` helper)

## Database schema (last known-correct — verify against `prisma/schema.prisma` after `db pull`)

**Foundation:** `Business` (plan/tier/country-derived currency & timezone, no Somalia hardcoding, `settings` JSONB catch-all; gained `businessDayStartTime`/`businessDayEndTime` `@db.Time` columns 2026-07-22, defaults `00:00:00`/`23:59:59` — the single source of truth for Void/Refund day-boundary eligibility, see "Sales" below), `User` (email is the primary login identifier, not phone; `passwordHash` nullable for Google accounts; `failedLoginAttempts` incremented atomically), `Branch`, `Warehouse` (exactly one per business, enforced via `@unique` on `businessId`).

## Auth architecture (locked)

- **Signup + Login (built, 2026-07-20 — `src/{services,controllers,routes}/auth.*`, `src/lib/{session,otp,googleAuth,countryReference,businessSettings}.ts`):**
  - `POST /auth/signup` — one endpoint, both paths (`provider: "email" | "google"` discriminated union). Collects Business Name, Owner Name, Business Email (email path) or Google `idToken` (google path — the account's own verified email is used, never a client-supplied email, so a signup can't claim an email it doesn't control), WhatsApp Phone, Password (email path only), Country. Country auto-fills currency/timezone/phone-prefix via the `world-countries` + `countries-and-timezones` npm packages (real reference data, not hand-authored — neither package alone covers all three fields) — all three remain client-overridable per the locked spec. `Business.tier`/`plan` are hardcoded (see Known schema gaps). Terms/Privacy acceptance required (`termsAccepted`/`privacyAccepted: true`, literal booleans). Signup **auto-issues a session** (access token + refresh/CSRF cookies) — the owner is logged in immediately, doesn't need a separate login step after signing up.
  - WhatsApp phone-verification OTP is sent at signup (`OtpPurpose.signup`) but is **non-blocking** — nothing in the locked spec says phone verification gates account usability, unlike email. Verified separately via `POST /auth/signup/verify-phone-otp` (this endpoint wasn't explicitly pre-approved in the implementation plan; added because a send-only OTP with no way to complete it would be a dead end — flagging here rather than silently expanding scope).
  - Email verification (email path only — Google's own `email_verified` claim satisfies it immediately on the google path, same "presenting the token is the proof" logic Staff Invitation already uses): a token is emailed at signup, verified via `GET /auth/verify-email/:token`. Single-use by construction — the token is cleared on success, so a replayed link fails the lookup rather than needing a separate "already verified" check (a real, since-fixed bug: that separate check was originally unreachable dead code once the token-clearing behavior is in place).
  - `POST /auth/login` (email+password) and `POST /auth/google/login` — separate endpoints, matching the doc's naming (`login` vs `google/login`). `POST /auth/google/identify` — not spec'd behaviorally anywhere except the name; implemented as a pre-check the frontend calls after obtaining a Google ID token, before deciding whether to render a login or signup flow: verifies the token, returns `{exists, hasPasswordAccount, email, name}`. **This is an interpretation, not a certainty** — confirm if a real frontend ends up wanting something different.
  - **Google account-linking:** a Google login matching an existing *password-only* account (no `oauth_provider` set) is a hard `409`, never a silent auto-link. Confirmed decision, not a default — verified no code path can create a second user row or touch the existing one's `password_hash` for this case.
  - **Password policy:** min 8 chars, 1 upper, 1 lower, 1 number, 1 special char (`passwordSchema` in `src/lib/password.ts`, reused everywhere a password is set). Last 3 passwords blocked from reuse (`password_history`, populated on every account-creating/password-setting path).
  - **Lockout:** 5 failed attempts → `locked_until = now + 15min` (`FAILED_LOGIN_LOCK_THRESHOLD`/`FAILED_LOGIN_LOCK_MINUTES` in `auth.service.ts`, not env vars — deliberate, promote to config if that ever needs to be tunable). The lock check runs *before* password verification, so a correct password during an active lock still gets `423`, not a bypass. Counter resets to 0 on any successful login.
  - **Email verification gates:** `emailVerifiedAt` is real now, but nothing currently reads it as a gate — Password Reset (the thing it's documented to gate) is out of scope this pass. Security-alert emails and staff-invite acceptance's own verification are unaffected (staff-invite has its own, separate verification-by-token-possession logic, unrelated to this field).
- **Staff Invitation (built, 2026-07-20 — `src/{services,controllers,routes}/staffInvite.*`):**
  1. Owner enters Full Name, Email, Phone, Role (`POST /staff/invite`, owner-only, `manager` deliberately excluded — confirm if that's wrong).
  2. System emails an Accept Invitation link: `${APP_BASE_URL}/invite/<token>`.
  3. Invitee clicks → `GET /staff/invite/:token` shows business name + role → sets a password + checks a Terms/Privacy consent box → `POST /staff/invite/:token/accept`.
  4. Account activates immediately, `email_verified_at` set at that moment (presenting the mailed token *is* the verification). **No OTP anywhere in this flow.**
  5. Same login rule applies afterward: email + password only — now real, via `POST /auth/login`.
  - Invitable roles exclude `owner`/`super_admin` (enforced server-side via the Zod enum, not just UI). Invite token is 256-bit random, stored in `staff_invites.token` as plaintext (not hashed) — a deliberate choice matching the schema's own naming (contrast `sessions.refresh_token_hash`, which is hashed); revisit if that stops feeling right.
  - No resend/list/revoke-invite endpoints exist yet — a duplicate pending invite for the same business+email is a hard 409, not a resend.
  - QA caught and this fixed a real race: accepting the same invite token twice concurrently used to be able to 500 instead of cleanly 409 (the invite-claim wasn't atomic). Fixed by claiming the invite via `updateMany({ where: { id, accepted_at: null } })` and checking the row count *before* creating the user, inside the same transaction — not relying on an incidental `users.email` unique-constraint collision as the safety net. Regression test: `tests/staffInvite.accept.test.ts` ("only lets one of two concurrent accepts win").
  - Known minor gap, not fixed: `passwordSchema` (`src/lib/password.ts`) has no max length. Low risk (100kb body limit already bounds it), but worth a cap if this becomes a concern later.
- **New Device / High-Risk Login:** optional per-business toggle in `Business.settings` (`security.requireOtpForNewDevices` JSON key, default OFF — read via `src/lib/businessSettings.ts`). ON: a device is "known" only while it has an **active** session (`revoked_at: null`, `expires_at > now`) for that exact `(user_id, device_id)` pair — logging out (or a session expiring) resets that device's trust, it does not stay recognized forever. OFF (default): no OTP ever, on any device. QA caught and this fixed a real gap: the original check only tested whether a session had *ever* existed for that device, so a logged-out or revoked device stayed permanently trusted even with the toggle ON, silently defeating the feature. Regression tests: `tests/auth.login.newDeviceOtp.test.ts` ("re-challenges a device once its only session has been revoked/expired"). The OTP itself (`OtpPurpose.new_device_login`) goes via WhatsApp under the `SECURITY` category — a deliberate carve-out from the general Notification Routing rule below (SECURITY is normally email-first); the challenge has to reach the device being verified, so WhatsApp isn't optional here the way it is for other SECURITY alerts. No session/tokens are issued while `requiresOtp: true` is pending — verified no `Set-Cookie` header on that response. `otp_challenges.max_attempts` (5) locks the challenge after repeated wrong codes.
- **Refresh tokens:** httpOnly cookie (`refresh_token`, path `/auth`, never in the JSON body) + a readable double-submit `csrf_token` cookie, both reissued on every login/refresh. `requireCsrf` middleware (`src/middleware/csrf.ts`, timing-safe compare) gates only `POST /auth/refresh` and `POST /auth/logout` — the two endpoints that act purely on the ambient cookie; signup/login/google endpoints establish a *new* session rather than acting on one, so they're deliberately not CSRF-gated. In production the cookies are `SameSite=None; Secure` (the frontend is a separate origin per this doc's own "still separate HTML/React prototypes" note), which means the double-submit cookie is the *primary* CSRF defense here, not decorative — cross-origin `SameSite=None` cookies bypass the browser's own same-site protection. **Remember-me mechanics:** every refresh updates the *same* session row — new `refresh_token_hash` (rotation; the old raw token stops matching anything and further use of it is rejected), `expires_at` reset to `now + 7d` **unconditionally** regardless of `remember_me`, while the reissued cookie's own `Max-Age` (30d / 12h) is computed fresh from `remember_me` every time, not just at login. This reconciles "`expiresAt` is always 7 days" (true at every point it's written) with remember-me actually working across repeated use — a remembered session's 7-day DB window keeps sliding forward as long as the up-to-30-day cookie prompts activity; a non-remembered session's 12h cookie vanishes client-side long before the 7-day server cap would matter. **Accepted gap:** rotation updates in place rather than chaining session rows, so replayed-old-refresh-token *reuse detection* isn't built (the schema has no `previous_hash`/`replaced_by` column) — a stolen-then-rotated-away token simply fails on reuse (safe), but there's no alerting/family-revocation on that event.
- QA caught and this fixed a second real race, same TOCTOU class as staff-invite's: two concurrent signups with the same email could have the loser hit an uncaught Prisma `P2002` → generic `500` instead of a clean `409` (the pre-transaction existence check is a courtesy, not a guard — the unique constraint is the real one). Fixed by catching `P2002` on the `tx.users.create()` call inside the transaction and re-throwing as `conflict()`. Regression test: `tests/auth.signup.test.ts` ("only lets one of two concurrent same-email signups win").
- **RBAC:** `requireRole(...roles)` middleware. `super_admin` bypasses every check. `custom` role is fail-closed (403) until a permissions-evaluation engine exists — `User.permissions` JSON is present but unused, don't wire partial support for it. `req.auth` (set by `authenticate.ts`) carries `{userId, businessId, role, name}` — `name` was added 2026-07-21 (pulled from the JWT payload, which already had it) specifically so every business-module service can audit-log without an extra DB round trip to look up the actor's name; `staffInvite.service.ts` predates this and still does its own lookup, which is fine, just don't copy that older pattern in new code.
- **Void vs Refund (Sales) — built 2026-07-22, Session 3B:** Void = same business day only, by the cashier who created it (owner/super_admin also pass; manager does **not** bypass — enforced via `requireRole` excluding manager entirely from the route, plus a service-level `sale.cashier_id === actor.userId` check for the cashier case specifically), restores inventory using the sale's original item quantities inside the same transaction. Refund = after day-close only, owner/manager only, financial-only — no inventory restore (that stays with the not-yet-built Returns module); creates a separate reversal `Sale` row (`refundOfSaleId`, every money figure negated) rather than modifying the original's financial fields. **Day-close is now schema-backed, not hardcoded**: `Business.businessDayStartTime`/`businessDayEndTime` (defaults `00:00:00`/`23:59:59`, reproducing the prior "same calendar day in `Business.timezone`" rule exactly) via `src/lib/businessTime.ts`'s `getBusinessDay`/`isSameBusinessDay`. Both a sale already voided and a sale already refunded are blocked from the other transition (and from repeating the same one) by one atomic guarded `status` update (`WHERE status = "completed"`) — see "Sales" below for the full reasoning on why that's read as compliant with "never modify the original Sale financially."

## Business modules (Branches, Payment Methods, Products — Sessions 1-2 of the rebuild, built 2026-07-21)

Shared infrastructure every module from here on reuses — get this right once, don't re-derive it per module:
- **`src/lib/ownership.ts`** — `assertOwned(row, businessId, label?)` / `getOwned(fetchPromise, businessId, label?)`. Throws the identical `notFound()` (404) whether a row doesn't exist or belongs to a different business — a caller can never distinguish the two. QA-verified this actually holds (no Prisma error, timing difference, or response-shape difference leaks cross-business existence) before trusting it as the pattern for every module.
- **`src/lib/pagination.ts`** — `paginationQuerySchema` (`page`/`pageSize`/`sort`/`order`/`search`, composable via `.extend()`), `resolveListQuery(query, {sortableFields, defaultSort, searchableFields})`, `paginate(rows, total, page, pageSize)` → `{data, pagination}`. Does **not** wrap the actual Prisma `findMany`/`count` call — this repo has no ORM-abstraction layer anywhere, each service still writes its own query using the resolved pieces directly. Unknown `sort` falls back to `defaultSort` rather than 400ing (QA-confirmed this is what actually happens, not just the documented intent). `pageSize` is capped at 100, floor 1 — out-of-range values 400.
- **`src/validation/common.schema.ts`** — `idParamSchema` (UUID path param), shared across every module rather than redefined per-module.

**Branches** (`src/{validation,services,controllers,routes}/branch.*`) — create/list/get/update/archive/restore, `requireRole("owner", "manager")` (`super_admin` bypasses via `requireRole` itself). `managerId`, if supplied, is checked via `getOwned` to confirm the referenced user belongs to the same business — **it does not check that user actually holds a manager-type role** (QA-flagged, not a bug: matches what was actually asked — "minimal CRUD" — but worth a conscious decision before other modules copy this pattern for their own cross-references, e.g. Products' category/supplier fields).

**Payment Methods** (`src/{validation,services,controllers,routes}/paymentMethod.*`) — identical shape to Branches (create/list/get/update/archive/restore, same RBAC), no cross-reference field.

Branches and Payment Methods: archive/restore round-trip (not just one-way archive — added beyond the doc's literal "CRUD" since a permanently-one-way archive would be a dead end, same reasoning as Auth's phone-OTP-verify endpoint), audit-logged on create/update/archive/restore via the existing `writeAuditLog` helper, no transactions needed (single-table writes only). No rate limiter attached (rate limiting only exists on `/auth`/`/staff` routes so far — consistent with hardening roadmap Session 9 "distributed rate limiting" being not-yet-started, not a regression).

**Products** (`src/{validation,services,controllers,routes}/product.*`) — `POST /products`, `GET /products` (paginated), `GET /products/:id`, `PATCH /products/:id`, `DELETE /products/:id` (archive), `POST /products/:id/restore`, `POST /products/:id/stock-adjustment`.

- **RBAC (a deliberate design split, not from explicit doc spec):** create/update/archive/restore = owner+manager only. List/get = owner+manager+accountant+storekeeper (accountant needs cost visibility for reporting; storekeeper needs to know what they're stocking). Stock-adjustment = owner+manager+storekeeper (storekeeper is the role that actually does physical stock counts). Cashier is excluded from every Products endpoint — POS-only, product lookups for checkout belong to the not-yet-built Sales module, not general product management. Shareholder and `custom` get no access anywhere, per the general rule.
- **Optimistic locking, for real this time:** every mutating endpoint (update/archive/restore) requires the client to send the `version` it last read; the write is `updateMany({where: {id, version: expectedVersion}, data: {..., version: {increment: 1}}})`, checking the returned count — a stale version is a clean `409`, not a silent overwrite. Same pattern for stock-adjustment against `branch_inventory.version`.
- **Categories:** `categoryId` is validated for same-business ownership via `getOwned` if supplied, but **there is no Category CRUD module in this repo** — categories can currently only be created via direct DB access. Not an oversight; Categories was never asked for as its own module. Don't build features that assume category management exists through the API.
- `images` is deliberately not exposed anywhere in the API — dormant field (no upload feature exists), stays at its DB default.
- **Cost-price-change → PriceHistory:** `PATCH /products/:id` requires a `reason` **only** when `costPrice` is actually changing (compared via `Prisma.Decimal.equals()`, so string/number formatting differences like `"10.00"` vs `10` correctly don't count as a change) — not when other fields change, not when `costPrice` is sent but numerically unchanged. When it does change, writes a `price_history` row inside the same transaction as the product update. `sellingPrice` changes are **not** tracked in PriceHistory — only `costPrice`, matching what was actually asked.
- **Stock-adjustment direction is client-supplied, not inferred from `adjustmentType`** — confirmed decision. `correction`/`opening_balance`/`transfer` don't have an unambiguous inherent direction the way `increase`/`decrease`/`damage`/`loss`/`found` do, so the request body carries both `adjustmentType` (why, for audit/reporting) and `direction: "increase"|"decrease"` (which way stock actually moves) as separate fields. If no `branch_inventory` row exists yet for `(branch, product, size)`, an `increase` creates one (covers `opening_balance`); a `decrease` against nothing is a clean `409`. The lookup accounts for the documented `size IS NULL` dedup limitation (picks one row deterministically, doesn't corrupt data if duplicates exist — QA-verified, see below).
- **Money/quantity precision:** `costPrice`/`sellingPrice`/`minStockLevel`/stock-adjustment `quantity` all reject input with more than 2 decimal places at the Zod layer (`decimalField()` in `product.schema.ts`) — added after QA found that sub-cent input (e.g. `10.001`) used to slip through, get treated as "changed" by the pre-rounding `Decimal.equals()` compare, and either write a phantom PriceHistory row (`old_price === new_price` after DB rounding) or trip a DB `CHECK` constraint mid-transaction and surface as an unhandled `500`. Now rejected cleanly at `400` before reaching the service.

**QA caught and this fixed a genuinely critical bug**, found outside the specifically-requested scrutiny areas: `updateProductSchema` originally reused `sizes`/`unitType`/`packagingHierarchy` field definitions that carried `.default(...)` (meant for create). Zod's `.default()` substitutes whenever the resolved value would be `undefined` — including "key omitted from the request" — **regardless of `.partial()`** being applied on top. Every `PATCH /products/:id` that didn't explicitly resend all three fields was silently wiping them back to `[]`/`"each"`/`{}`, overwriting real data on any ordinary partial update (e.g. changing just the `sku`). Fixed by giving `updateProductSchema` its own non-defaulted definitions for those three fields instead of reusing the create-only versions. Regression test: `tests/product.qa.additional.test.ts` ("a PATCH that only changes sku must NOT reset sizes/unitType/packagingHierarchy"). This is exactly the kind of bug `.partial()` + `.default()` combinations should be assumed to have until proven otherwise — watch for the same pattern in Sales/Debts/Expenses' update schemas.

## Sales — Session 3A (Sale Creation), built 2026-07-22

`src/{validation,services,controllers,routes}/sale.*` — `POST /sales`, `GET /sales` (paginated, filters: `status`/`branchId`/`dateFrom`/`dateTo`), `GET /sales/:id`. Void/Refund (`POST /sales/:id/void`, `POST /sales/:id/refund`) were deliberately isolated from this session per the user's own framing — see "Sales — Session 3B" immediately below for those.

- **`sales.items` is a JSON column, not a relational table.** The live schema already locked this shape before this session started — Requirement "each line permanently stores its price snapshot" is satisfied by what `createSale` writes into that JSON array (`productId`/`productName`/`size`/`quantity`/`sellingPriceAtSale`/`costPriceAtSale`/`lineSubtotal`/`discount`/`tax`/`profit`), never a separate `SaleItem` table.
- **Architecture decision — Inventory Ledger:** extended the existing `inventory_adjustments` table (new `AdjustmentType` enum values `sale`/`void`) rather than building a parallel movements table. One row per line item, `reason: "Sale ${sale.id}"` for traceability. Confirmed with the user before implementation. (Originally shipped without a `sale_id` FK column, reasoning "nothing programmatic needs that join yet" — the user flagged this before 3B started, and it was right: `inventory_adjustments.saleId` was added in 3B, see below, and `createSale`'s own inserts were retrofitted to populate it too.)
- **Architecture decision — Sale Number vs Receipt Number:** `sales.id` (already a `generateId()` UUID) *is* the immutable, never-reused Sale Number — no schema change needed for it. Receipt Number is new: `receipt_id` now gets populated with `INV-<business-local-year>-<6-digit-sequence>`, sequential per business per year, backed by a new `receipt_counters` table (`business_id`+`year` unique, `last_number`) and a single atomic `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING` statement (`src/lib/receiptNumber.ts`) run inside the sale's own transaction — never `SELECT MAX+1`. Year is computed from `Business.timezone` via a new `src/lib/businessTime.ts` (`getBusinessLocalYear`), written as a general utility (not receipt-number-specific) so Session 3B's Void/Refund day-close check reuses it instead of re-deriving timezone math.
- **Idempotency-Key, built for real for the first time** (`idempotency_keys` table already existed but nothing read/wrote it before this session): `src/middleware/idempotencyKey.ts` (`requireIdempotencyKey` — 400 if the header is missing, thin/validation-only like `csrf.ts`) + `src/lib/idempotency.ts` (`getReplayedResponse`/`claimIdempotencyKey`/`completeIdempotencyKey`). Two-phase: claim happens as the *first* write inside `createSale`'s own `$transaction` (relies on the table's `@@unique([business_id, key, endpoint])` constraint — a collision throws `conflict()`, rolling back the whole attempt and leaving the key free if the earlier attempt genuinely failed); complete happens as the *last* write in the same transaction, storing the exact JSON-normalized response body so a replay is byte-identical to the original. QA-verified this closes the true-concurrent-brand-new-key race (two simultaneous requests sharing a never-before-seen key — exactly one 201, the other a clean conflict, never a second sale). Designed for reuse as-is by Debts' payment endpoint (and 3B's Void/Refund) per the original session-breakdown plan — no new lib code expected there.
- **Stock decrement is atomic-conditional, not read-then-write** — worth being explicit about given the existing documented `branch_inventory` NULL-size dedup gap (a plain btree unique index doesn't dedupe `size IS NULL`, so more than one qualifying row can theoretically exist). Per line: a `findFirst` (deterministic `orderBy: id asc`) picks **which row** to target — unavoidable given that gap — but the accept/reject decision itself is made by the DB, atomically, in the same `updateMany` statement that writes (`WHERE id = row.id AND quantity >= requestedQty`), re-verified against live state at write time, not from the earlier read. For the common case (non-null `size`) the unique index guarantees `findFirst` can only ever match one row anyway.
- **Money math is entirely `Prisma.Decimal`, never `number`/`float`.** Client sends one optional sale-level `discount` (`fixed`|`percentage`) and one optional `taxRate` (percentage); server prorates both down to each line by that line's share of subtotal, remainder assigned to the last line, so per-line amounts always sum exactly to the sale-level totals. **QA caught and this fixed a real Decimal-rounding bug**, found outside the specifically-requested scrutiny areas: each line's raw subtotal (`sellingPrice × quantity`) was originally summed *unrounded* for the sale-level `subtotal`, while each line's own stored snapshot was rounded to 2dp independently — two lines each with a raw subtotal of exactly `0.005` each round *up* to `0.01` individually (stored sum `0.02`), while the true unrounded total (`0.01`) rounds to `0.01` once. Fixed by rounding each line's subtotal to 2dp at the single point it's first computed and using that same rounded value everywhere downstream (sale-level sum, discount/tax proration base, and the stored snapshot) — sale-level `subtotal` is now the sum of the lines by construction, not by coincidence. Regression test: `tests/sale.test.ts` ("keeps item-level lineSubtotal snapshots summing to the exact sale-level subtotal").
- No price-override field this session — the spec only named it in the audit-events list ("if applicable"), nothing in the schema marks a line as overridden, and nothing else asked for it by name. `sellingPriceAtSale` is always the product's current `selling_price` at sale time. Flag if a real price-override capability is actually wanted — cheap now, more disruptive once 3B builds on this shape.
- No packaging-level conversion on sale lines (unlike Products' stock-adjustment endpoint) — a line's `quantity` is in the same base ("each") unit `branch_inventory.quantity` already tracks. `inventory_adjustments` rows written by a sale record `packaging_level: "each"`.
- **RBAC (inferred, not a copy of the actual 8-role recovery-doc matrix — that document isn't a file in this repo):** create = owner/manager/cashier (cashier explicitly doc-confirmed; storekeeper explicitly has zero sales access, also doc-confirmed). List/get add accountant (reporting/reconciliation visibility, same reasoning as Products' accountant read-access). Shareholder/custom: no access anywhere, matching every other module. Flag if the real matrix says otherwise.
- **`decimalField()`** (the 2dp-precision Zod guard) moved from `product.schema.ts` into `src/validation/common.schema.ts` and is now exported/shared — `product.schema.ts` imports it instead of keeping its own copy. Behavior-identical; existing Products tests are the regression check (still passing).
- **Extension points verified, none built this session** (per explicit user instruction — see the Session 3A plan for the full table): CRM/Customer Purchase History (`customer_phone` already the natural join key), Accounting (figures already server-computed/immutable), Debt Module (`debts.sale_id` already exists, nullable — zero Sale-side change needed), Reports/Analytics (every needed field already exists, read-only), Notification Events (`SaleCreated` — no event bus existed yet at the time, real gap; built for real in 3B, see below), Branch-level Inventory isolation (already true from Session 2's schema, this session inherits it directly), Business Timezone/Daily Session Close (`getBusinessLocalYear` deliberately general-purpose — 3B added `getBusinessDay` alongside it in the same file).
- No per-sale notification is sent (no `SaleCreated` → WhatsApp/Email spam) — matches the explicit "notification restraint" requirement; sale creation only saves data and writes the audit trail. (`SaleCreated` *is* published as a domain event as of 3B — that's not the same thing as a notification; see below.)

## Sales — Session 3B (Void, Refund), built 2026-07-22

`src/services/sale.service.ts` gained `voidSale`/`refundSale`; `src/{controllers,routes}/sale.*` gained `POST /sales/:id/void` and `POST /sales/:id/refund`. Builds directly on 3A's ledger and receipt-numbering shape — the Architecture Lock rule for this session was "extend, don't rebuild," and nothing in 3A's shape needed to change to accommodate this.

- **Final State Protection** (a sale reaches exactly one terminal state — `Completed→Voided` and `Completed→Refunded` allowed, all four other transitions/repeats forbidden) is enforced by **one atomic guarded status update** on both paths: `tx.sales.updateMany({ where: { id, business_id, version, status: "completed" }, data: { status: newStatus, ... } })`, checking `result.count`. A `count === 0` covers "already voided," "already refunded," and "modified concurrently by another request" all at once, symmetrically, with no separate existence-check query needed.
- **"Refunds must never modify the original Sale" is read as the financial record specifically, not lifecycle status** — a deliberate interpretation, stated up front for review rather than assumed silently. Refund transitions the original's `status` (`completed`→`refunded`, same atomic guard as Void) but never touches `subtotal`/`discount`/`tax_amount`/`total`/`profit`/`items` — those stay exactly as `createSale` wrote them, permanently. Taken completely literally (zero field writes including `status`), Final State Protection becomes unenforceable atomically without a second existence-query, which is what this reading avoids.
- **Refund reversal** = a brand-new `sales` row (`refund_of_sale_id = original.id`, a column that already existed in the live schema before this session — the DB was designed for exactly this shape). Every money figure negated 1:1 from the original (`subtotal`/`discount`/`tax_amount`/`total`/`profit` all ×`-1`) so `total = subtotal − discount + tax` still holds for the reversal row too. `items` copied verbatim (informational — refund is financial-only, no inventory write at all). Gets its own new receipt number from the same per-business-per-year sequence (a refund is its own customer-facing financial event, not free). `chk_sales_total_nonneg: CHECK (total >= 0 OR refund_of_sale_id IS NOT NULL)` — confirmed by reading the live constraint before writing this code, not assumed — already permitted a negative total specifically for this case; zero migration needed for it.
- **No `refund_reason` column** — `sales.void_reason` already existed for Void and is populated directly; there's no analogous refund field, and reusing `void_reason` for refunds would be actively misleading. The refund reason is required at the Zod layer and stored in the `AuditLog` entry (`sale.refunded`), this repo's existing canonical "why" record.
- **Exact inventory restoration on Void** — reads the sale's own immutable `items` snapshot (3A's price-locked JSON, never recomputed from current stock) and atomically increments `branch_inventory` by those exact quantities, one `inventory_adjustments` row per line (`adjustment_type: "void"`, `sale_id` set). `adjustment_amount` is stored positive (`quantityAfter − quantityBefore`) — the mirror of how a sale's own decrement stores `quantityBefore − quantityAfter` — required by the live `chk_inventory_adj_amount_positive` constraint.
- **Business Day is now schema-backed** (`Business.businessDayStartTime`/`businessDayEndTime`, `src/lib/businessTime.ts`'s `getBusinessDay`/`isSameBusinessDay`) rather than hardcoded same-calendar-day math — see the schema section above and the Auth Architecture's Void-vs-Refund entry. `businessDayEndTime` is stored but **not yet read** by Void/Refund eligibility (a rolling 24h window from `start` alone is sufficient and unambiguous for that purpose) — it becomes load-bearing whenever Daily Reports/Cash Closing/Shift Closing get built. Unit-tested directly in `tests/businessTime.unit.test.ts` (non-default start times, the boundary instant itself, month/year/leap-year rollover, a non-whole-hour-offset timezone) — added during this session's QA pass specifically because the integration tests only ever exercised the *default* start time.
- **Domain events are real now, not just documented extension points**: new `src/lib/events.ts`, a typed `EventEmitter`-backed `domainEvents.publish(name, payload)` singleton for `SaleCreated`/`SaleVoided`/`RefundCreated`. Published strictly **after** each operation's transaction commits, never from inside it. `createSale` (3A) was retrofitted to publish `SaleCreated` too, for consistency. No subscriber exists yet anywhere in this repo (Notification/Analytics/CRM/Accounting are all still unbuilt) — this is the publish side of the loose-coupling rule ("Sales must never call those modules directly"), proven by tests attaching a temporary listener, not by an actual subscriber.
- **RBAC**: Void = owner/cashier only (`requireRole("owner", "cashier")` — **manager is deliberately excluded from the route entirely**, unlike everywhere else in this module where manager has broad access; `super_admin` still bypasses via `requireRole` itself). A cashier may only void **their own** sale (`sale.cashier_id === actor.userId`, enforced in the service — role membership alone can't express per-resource ownership). Refund = owner/manager only, no cashier, no per-sale ownership restriction (any owner/manager can refund any sale in the business).
- **Idempotency-Key reused as-is** from 3A's `src/lib/idempotency.ts` (no new lib code, matching the original session-breakdown plan) — both new endpoints require the header and use the same claim-inside-transaction/complete-at-the-end two-phase pattern, scoped per-sale (`POST /sales/${id}/void` as the logical endpoint string, not a bare `"POST /sales/:id/void"`, so a reused key can never cross-contaminate a different sale's operation).
- **QA caught and this fixed two real bugs**, both outside the specifically-requested scrutiny areas:
  - `tests/helpers/cleanup.ts` nulled `sales.refund_of_sale_id` before bulk-deleting to break the self-referencing FK — but a refund reversal row's negative `total` is only permitted by `chk_sales_total_nonneg` *while* that FK is still set, so nulling it first violated the constraint the moment any test created a real refund. Fixed by deleting reversal rows (`refund_of_sale_id IS NOT NULL`) before the rows they reference, instead of nulling anything.
  - Under genuine 5-way concurrent sale creation, one request threw a Prisma `P2028` (interactive-transaction timeout, 5s default). Root cause: `getNextReceiptNumber`'s atomic per-`(business, year)` counter row is a deliberate serialization point — that's what atomic sequential numbering requires — and Neon's serverless HTTP driver adds real per-query latency, so a transaction queued behind several others waiting on that same row can legitimately exceed 5s under load with nothing actually deadlocked. Fixed by raising the transaction timeout to 15s (`SALE_TRANSACTION_OPTIONS` in `sale.service.ts`, applied to all three of `createSale`/`voidSale`/`refundSale`).

## Engineering standards

Write clean, modular, secure-by-default, tested, production-ready code. Follow SOLID, DRY, KISS, YAGNI. Don't design for hypothetical future requirements — this repo already has a 15-session roadmap of *known* future work; don't invent more.

**Security, always:** parameterized queries only (Prisma handles this — never drop to raw SQL with string interpolation), validate every input at the boundary (Zod), sanitize user data, never hardcode secrets, never log tokens/passwords/PII. Guard against SQL/NoSQL injection, XSS, CSRF, SSRF, command injection, path traversal, auth/authz bypass.

**Database:** use migrations, never hand-edit the live schema outside Prisma, never delete production data, protect data integrity with `CHECK` constraints and transactions where multiple tables move together.

**Decision-making:** understand the problem → analyze existing code → find root cause → consider options → pick the safest → implement → test → explain. Never guess an API shape or a database field. If information is missing, ask — don't invent.

**Testing:** every feature needs unit + integration tests; every bug fix needs a regression test. Nothing is "done" without tests passing. Invoke the `qa-tester` subagent after any feature or fix — it never writes source code, only tests and reports.

**Approval:** small bug fixes, docs updates, and minor refactors can proceed directly. Database schema changes, breaking API changes, and large architectural changes should be confirmed first — this repo has already had one total-loss incident from moving fast without version control; don't compound that by moving fast without discussion on anything hard to reverse.
