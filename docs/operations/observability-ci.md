## Structured logging — allowlist, not a blacklist

`src/lib/logger.ts` writes one JSON object per line to stdout (`logRequest`, `level: "info"`) or stderr (`logUnhandledError`, `level: "error"`) — no third-party logging library, deployed as-is to Railway, which ingests stdout/stderr directly as its log stream.

The allowlist is enforced two ways, not one: the TypeScript input types are closed (no index signature), **and** every writer function constructs its output object field-by-field rather than spreading a caller-supplied object — the second layer matters because TypeScript's excess-property checking only fires on object literals at the call site, not on a variable passed through, so field-by-field construction is what actually prevents an unlisted key from ever reaching stdout/stderr regardless of what a caller passes.

**Request log fields (exhaustive):** `level`, `event`, `method`, `path`, `status`, `durationMs`, `requestId`, `businessId` (only when `req.auth?.businessId` is already populated — read inside the response's `finish` handler, so it's correctly present for an authenticated request and correctly absent otherwise). Request/response bodies, headers, and cookies are never passed to the logger at all — there is no code path by which they could reach it, since the logger's function signatures don't accept them.

**Error log fields (exhaustive, unexpected/unhandled errors only):** `level`, `event`, `requestId`, `method`, `path`, `errorName` (the error's own constructor name — `"TypeError"`, `"PrismaClientKnownRequestError"`, etc.), and `errorCode` only when the caught value has a `.code` string matching a restrictive safe-taxonomy pattern (`^[A-Z][A-Za-z0-9_]{0,31}$`, e.g. Prisma's own `P2028`/`P2002`). **`.message` and `.stack` are never logged for an unexpected error, under any circumstance** — this is a deliberate, real reduction from this repo's prior behavior (a raw `console.error(err)` including the full message and stack), traded because message content on an unexpected error is untrusted by construction (a Postgres constraint-violation message can embed the literal conflicting value; a provider SDK error can echo raw request/response content). A `ZodError` or `AppError` (this repo's own deliberate business/validation error type) is a *handled* outcome and is never logged as an error at all — only response-shaped, matching this file's pre-existing distinction.

Proven by test, not just asserted by code review: `tests/logger.unit.test.ts` covers the allowlist at the unit level (including a hostile-input test proving extra properties on a caller's object can't be smuggled through) and, critically, a real end-to-end HTTP request (`POST /auth/login`) carrying nested objects and arrays of sensitive sentinel values (password, OTP, IBAN, phone, email) in the body plus sentinel values in the `Authorization` header and a cookie — capturing all `console.log`/`console.error` output for that request and asserting none of the sentinels appear anywhere in it.

## Request-ID correlation

`src/middleware/requestId.ts` is the first middleware in `src/app.ts`'s chain — before `helmet()`, `cors()`, the raw-body Resend webhook route, and `express.json()` — so every request, including the one route shape that never touches `express.json()`, gets a correlation ID and (via `src/middleware/requestLogging.ts`, mounted immediately after) an accurate end-to-end duration measurement.

An inbound `X-Request-Id` header is trusted only if it matches `^[A-Za-z0-9_-]{1,64}$`; anything else (too long, empty, containing a space/semicolon/slash/control character) is discarded in favor of a freshly generated UUID — closing a log-injection/correlation-collision vector, not just a cosmetic validation. The resolved ID is always set on the response's own `X-Request-Id` header, and is included in every error response body (`ZodError`/400, `AppError`/4xx, and the generic 404/500 fallbacks) alongside the existing response shape — additive only, no existing field removed or renamed.

`tests/requestId.test.ts` covers valid/invalid inbound headers (both through a real HTTP round-trip for every transmittable case, and directly against the middleware function for the one case — an embedded newline — that Node's own HTTP client library refuses to even transmit, so it's tested as defense-in-depth beyond what the transport layer already blocks) and requestId propagation into all three error-response shapes.

## `/health` vs `/ready`

Both confirmed absent before this session via direct search of `src/app.ts`/`src/routes/`, not assumed. Mounted immediately after request-ID/logging middleware, before `helmet()`/`cors()`/body parsing — no rate limiter added (none exists globally in this repo today; out of this session's scope).

- **`GET /health`** — pure liveness. Returns `200 {status: "ok", requestId}` unconditionally. Never touches the database (proven by test: a `jest.spyOn(prisma, "$queryRaw")` spy asserts zero calls during a `/health` request).
- **`GET /ready`** — the one real dependency this app has: a short-timeout (3000ms), read-only `SELECT 1`, raced against a timer so a hanging connection can't hang the probe itself. `200 {status: "ready", requestId}` on success, `503 {status: "not_ready", requestId}` on failure or timeout — the caught error's own content is always discarded, never surfaced. Neither response ever includes a stack trace, connection string, provider detail, environment value, or build secret — proven by test with a simulated failure whose message is deliberately crafted to look like a real connection string, asserting it never appears in the response body.

## CI — fork-safe, ephemeral-database GitHub Actions workflow

`.github/workflows/ci.yml`, confirmed newly created (no `.github/workflows/` directory existed at all before this session). Triggers on `pull_request` only, **never** `pull_request_target` — this repository is genuinely public (confirmed directly against the live GitHub page, not assumed), so a fork PR is a real, live possibility. `pull_request` gives a fork PR's run a read-only `GITHUB_TOKEN` and no access to repository secrets by default; `pull_request_target` runs in the base repo's own secret-bearing context while typically checking out the fork's own untrusted code — exactly the class of exploited Actions vulnerability avoided here by construction, not by a runtime filter.

**Five jobs:**

1. **`checks`** — runs for every PR, same-repo or fork, with zero secrets referenced anywhere in its definition. Installs dependencies, `prisma generate`, `npx tsc --noEmit`, `npm run lint`, `npm run build`, and a curated, explicit allowlist of 14 test files confirmed (by direct import-graph inspection) to never import `src/app.ts`/`src/lib/prisma.ts`/any DB-touching test helper. `DATABASE_URL` and the four `JWT_*_SECRET` env vars are hardcoded placeholder strings — not secrets — present only so `src/lib/config.ts`'s Zod schema (loaded transitively the moment anything imports `src/app.ts`) doesn't reject module load; nothing this job runs ever attempts a real database query.
2. **`provision-db`** — same-repository PRs only (`github.event.pull_request.head.repo.full_name == github.repository`; shows as a genuinely *skipped* job in the Actions UI for a fork PR). Creates one ephemeral branch via the Neon Management API (`POST /projects/{project_id}/branches`, endpoint/request/response shapes confirmed directly against Neon's own current API reference before writing this workflow, not guessed), named `ci-pr-<PR number>-<run id>`. Warms the connection with a real, read-only `SELECT 1` via `psql` (retried up to 5 times), against the connection's own **direct, non-pooled `host`** field specifically (never `pooler_host`) — this repo's own Session A verification found the pooled endpoint intermittently throws `P2028` transaction-start faults under load.
3. **`db-integration-tests`** — same-repo only. Re-fetches this run's own branch password via `GET /projects/{project_id}/branches/{branch_id}/roles/{role}/reveal_password` (never passed through job outputs, even masked ones, since masked job outputs still render as `***` in the run's own Summary UI rather than being withheld entirely — re-fetching keeps the password from ever appearing there at all), masks it and the host immediately via `::add-mask::`, runs `prisma migrate deploy` + `prisma migrate status` against this run's own branch only, then the main test suite with the four quarantined tests excluded (see below). This is the **blocking** job.
4. **`quarantine-tests`** — same-repo only, `continue-on-error: true` at the job level (a real, documented GitHub Actions field — the job's own conclusion reports as passing to the PR checks UI regardless of whether its steps fail, while still running and its own result remaining independently visible). Runs *only* the four quarantined tests, informationally.
5. **`cleanup-db`** — `if: always() && needs.provision-db.result == 'success'`, so it correctly no-ops for a fork PR (where `provision-db` itself was skipped) and correctly always attempts cleanup for a same-repo PR regardless of whether the test jobs passed, failed, or errored. Deletes **only** the exact `branch_id` this same run's own `provision-db` job created and returned — never a name search, never a broader deletion. A delete failure reports (`::error::` + the branch id, identifiable later via its own naming convention) and fails only this one job; it never attempts to delete anything else.

**Structurally, not just conventionally, incapable of touching production**: the workflow file contains no reference to any secret named `DATABASE_URL` (or any name resembling the production secret) anywhere — the protection is that GitHub never injects a secret the workflow never names, not a runtime check that could itself have a bug. The only secret referenced anywhere in this file is `NEON_CI_TEST_API_TOKEN`, scoped (by the token's own Neon-side configuration, not by anything in this file) to the CI/test project only.

**Outstanding configuration dependency, not resolvable from inside this session**: `vars.NEON_CI_PROJECT_ID` (a repository *variable*, not a secret — project IDs aren't sensitive) must be set in **Settings → Secrets and variables → Actions → Variables** before this workflow can run its database-touching jobs; `secrets.NEON_CI_TEST_API_TOKEN` must already exist as a real, least-privilege, test-project-scoped secret (referenced here on the assumption it's already been provisioned, per this session's own authorization). Branch protection (requiring the `checks` and `db-integration-tests` jobs to pass before merge) is a separate, follow-up **repository setting**, not a code change — not yet configured, not treated as done here.

## Test quarantine — issues #6–#9

`tests/quarantine.config.js` is the single source of truth: four named entries, each with a file, a unique test-name fragment, a real linked GitHub issue number, an owner, and an expiry date (`2026-11-25`). `scripts/quarantinePattern.js` reads this file and builds two jest `-t` regexes — the negative-lookahead "exclude" pattern for the blocking `db-integration-tests` job, and the positive "include" pattern for the informational `quarantine-tests` job — so there is exactly one place this list can drift.

Never a bare `.skip()`, never a broad `testPathIgnorePatterns`. The script refuses to run (non-zero exit, listing every expired entry by id/issue/owner) once any entry's `expiryDate` has passed, unless a human has explicitly edited that entry's own `renewedUntil` field to a later date — a real, reviewed diff, never a silent auto-extension.
